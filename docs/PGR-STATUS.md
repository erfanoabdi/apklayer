# PGR (Punishing: Gray Raven) on the translated x86_64 route: status 2026-11-17

> 2026-11-17 cleanup (owner): the investigation tools of the PGR work (tools/ace/vmread and the gate/fsdiff/RE/netdump scripts added since 7534944), the patches 0062 (large_mmap knob) and 0071 (gate trace), tests/apps hello-atomics, hello-neondiff, hello-filedump and docs/PGR-ACE-STATIC.md were removed from main: none of them fixed the game. They stay in git history (before this commit) and in the local branches pgr-*. Tool names in the text below refer to them.

Short version: native arm64 works; the translated x86_64 route dies. The ACE anti-cheat (libanogs.so) runs a payload in its own arm64 VM. At about 80-90 s (about 29 s on an instance with ACE history) that payload enters a "net stage" that frees the same list of 64 blocks it already freed at start (a second free of the same 4 KiB blocks). Our free diagnostic refuses the frees ("no glibc chunk on entry", `BERBERIS_LOG_FREES=1`); the game freezes and dies 80-110 s later (SIGSEGV/SIGBUS). Native arm64 never takes that path.

## What is fixed (all in main)
- Thread-start trampoline in the preload (`vma_names.c`): ACE aborted the game 20-30 s after launch with it (removed).
- GL filter mapped by absolute path: `dlsym` returned NULL for GL functions the filter does not define, Unity crashed at 4-8 s on native (mapped by bare name, `cli/env.cpp`).
- Heavy-tier lobby noise: the 3D lobby is noise in two-gear mode; `lite-translate-or-interpret` draws it cleanly (3/3 vs 3/3). Per-app switch in the manager ("Lite translation") and `apklayer app <pkg> translation-mode default|lite|interpret`.

## How to reproduce the crash without any account
Fresh instances (`pgrp1..4` on the tester PC: hardlinked storage, empty PGR app-data, no login) storm 12/12 at 85-87 s even while the game sits at the first-run "Notice" dialog. Harness: `tools/ace/pgr-par.sh` (4 in parallel, early exit on the first storm line, about 2.6 runs/min). `pgrshared` (ACE state files present) storms at 27-31 s.

## What the payload does differently (the live lead)
`tools/ace/gate-diff.py`, patch 0071 (`BERBERIS_TRACE_GATE`), native side `tools/ace/pgr-gate-native.sh` (hardware execute breakpoints on `libanogs.so` +0x1f5200/+0x1f5238; uprobes/ptrace kill the game).
- One thread runs the VM; every host call goes through the gate at +0x1f5200 (callee = a libanogs-internal wrapper, x3 = VM pc).
- The streams are identical for the first 208 tokens and in the 2 s heartbeats. At the 20 s burst, native runs a full check round: reads `/proc/self/maps`, opens every mapped file and reads its first 4096 B (about 280 files), reads about 1600 `map_files` links and 123 fd links, scans `/proc` (about 400 entries, 2024 status reads), opens `/dev/random` about 2000 times (about 92k events). Translated runs about 21 opens in the same window (about 8-9k events) and skips that round. Nothing is gated by a failing syscall: every wrapper return class matches (GATE).
- With `APKLAYER_MAPS_CONSISTENT=4` (branch `pgr-mapfix`: served maps without host x86/JDK/translator lines) the VM takes the native branch at VM pc 0x141f0, then forks again 659 tokens later (VM pc 0x15b44: a loop at 0x15b8c calling libanogs +0x2d2a08 3084 times = a zip central-directory scan of base.apk, 2 x 1542 entries). Native also reads the central directory (33 reads of 4 KB); this loop is not what separates the routes.
- At 80 s translated runs the net stage (3 x select, then 12 x time/srand/rand/rmdir/__errno at VM pc 0x32760) and a third batch of 64 frees at VM pc 0x32824 = the storm. Native runs a small task at VM pc 0x33a54 instead.
- Open question: which VM-internal input selects the "skip the check round" branch. The first guest syscall after `stat /dev/virtpipe-sec` (ENOENT on both routes) is `openat /proc/self/maps` natively and `openat comm.zip` translated.

## Ruled out (each measured; baseline storm about 100%)
Instruction-set features, ID registers, HWCAP, SIGILL/signal frames (D); timing/CPU throttle (P); file and device presence (N, SERVE: every name in the served maps consistent); maps text (MAPFIX level 4: moves one fork, not the outcome); pid visibility (native in a private pid namespace survives 3/3; `APKLAYER_PIDS_VISIBLE=1` no effect); host leaks in status/dev/net/fd (R, REGRID: `APKLAYER_LEAK_VIEW=all` and every group); allocator layout (E4: the 4 KiB blocks are contiguous and untrimmed, the scudo knob only makes the same double free abort); stage-1 network bytes and the server reply (NET: byte-identical on both routes); ACE storage cycle (U2); translator gears (I1: interpret-only storms too; lite and default storm); atomics (AT: 196 checks, all gears); thread/TLS/allocator behaviour (TH: one real difference, `pthread_self()` in key destructors, patch 0062 in `pgr-th`: fixes it, does not stop the storm); `/proc` read semantics (PROC: merged; does not stop the storm); upstream Digitalis fixes (all already in the tree, coworker check); REGRID sweep of every default-off knob (maps view, host maps, MAP_NORESERVE, GL and kernel identity, timers, CNTFRQ, COUNT_MRS, cpufreq, lite, interpret-only, status-view preload, leak groups).

## Measured since the first version of this document (2026-11-17)
- Time dilation (TIMEDIL, branch `pgr-timedil`): ACE's timeline is sleep-driven (first 30 s: only gettimeofday, clock_gettime(REALTIME), nanosleep). Dilating wall clocks with real sleeps (k=4, 10) leaves the storm at 86-88 s (8/8); dilating clocks and sleeps by k=2 moves it to exactly 2x (167-171 s); CPU-time clocks are never read. Not a speed measurement.
- VMREAD (tools/ace/vmread): VM address space = a 0x44000-byte anon rw-p region (VM pc = offset in it; ctx+0x178 = base, ctx+0x108 = pc; handler table at [[ctx+0x190]+0x68]); the VM is arm64 with bits 24-30 of each word scrambled. The selector at the end of the check function is `cbz x20` at VM pc 0x160e8 (x20 = an earlier import-call result; origin not found).
- NATIVE ALSO STORMS when perturbed: a one-shot read at t=14 s through /proc/<pid>/mem (needs APKLAYER_PTRACER=1 on the tester, none on AWS as root) of the ABSENT (never touched) pages of small anon rw-p regions (about 50+ pages across at least two adjacent regions; present pages alone do nothing) makes native take the same VM path (short burst at 20 s, stage at 22 s, VM pc 0x32824 at 23 s) and abort with glibc "free(): invalid size". CPU starvation (taskset -c 0, hogs) does not. So the storm path is "ACE's verdict flips when it sees something about its memory/state", not a translator-only code path.
- RESIDENT/READER/TOUCH: the native 64 KB absent rw-p blocks are glibc thread-stack guard regions (MADV_GUARD, VmFlags `gu`, pagemap bit 58; a real phone has none): not what ACE tests. sigaltstack is SS_DISABLE on both routes. The translated route creates about 22 new 0x10000 rw-p anon blocks in the first 3 s: JVM arenas (libjvm mmap), resident when created. 68 arena-like glibc heaps translated vs 26 native; MALLOC_ARENA_MAX=1/2 changes that (68 -> 0/2) and leaves the storm unchanged (6/6). Nothing outside ACE's own guest threads reads /proc/<pid>/{mem,pagemap,smaps,clear_refs} or uses ptrace/process_vm_readv on the game before the storm (READER logger). MAP_NORESERVE default (0044) off: storm unchanged (1 valid pair).
- Stage-1 packets (NET interposer, tools in branch `pgr-net-netdump`): identical on both routes at every stable offset; the :10012 port is just another Tencent endpoint (in one translated run the first session went straight to :10012).

## Later results (2026-11-17, evening)
- MINCORE (branch pgr-mincore): ACE's canary protocol (8 small anon regions: madvise(12), DONTNEED, mincore, touch, mincore, DONTNEED, mincore) is identical on both routes, vectors 00/11/00, and the ~20 s check mincore(canary) answers absent on both. After it native runs a self-test block (tiny object test, an RWX page, a clone3 thread test that succeeds, a 2 s tick, a 17-step growing madvise series, a 2 s mincore heartbeat); translated skips it all (no pthread_create attempt at ~21.8 s: all 78 creations succeed). The "Thread-N" names are context hops of one VM thread.
- TOUCH (branch pgr-touch, patches 0072 log, 0073 stack pad): nothing in the translator touches guest anonymous pages; BERBERIS_STACK_PAD 1/2 and MAP_NORESERVE off do not move the storm. The native 64 KB blocks are glibc thread-stack guard regions (MADV_GUARD, VmFlags gu): artifacts of the AWS glibc/kernel, not Android.
- RESIDENT: 68 arena-like glibc heaps translated vs 26 native; MALLOC_ARENA_MAX=1/2 changes that and not the storm (6/6).
- ADDR: the 8 canary mmap hints are the END ADDRESSES OF ENTRIES OF THE SERVED /proc/self/maps, chosen by the VM after its line-reader loop (VM pc 0xa7b8; arg block a6dc, mmap import a700, result a71c); native passes 5 of 7 hints (the 2 misses are planned collisions: a hint inside a ---p reservation and a repeated hint), translated default misses 2 at different slots (end of [vdso] and a junction: hidden host mappings make the real address space differ from the served one), level 2 honours 7/7, level 4 misses 6/7. The storm is unchanged in all of them: hint==result alone is not the verdict, but the hints show that the VM's decisions are functions of the served maps' address geometry.
- NOT tested: a served maps that is TRUTHFUL about the real address space AND has the native geometry (all real mappings shown so that every gap shown free is really free; the translator's own reservations placed where the guest never looks), and the full conjunction of maps level 4 + the canary pattern of native + GATE's first-fork index as the metric.

## Results of 2026-11-17 night (state after the MAPFILES/LOOPDEC/CHAIN/CTXAUDIT/HOSTPATHS/SWEEP rounds)
- The storm needs `ano_tmp/kvcache8.dat`'s 3rd record from an earlier translated run (native 64 B / 2 records, translated 97 B+); swapping only the native kvcache8 in removes it (STATE). Native writes `atti_obv.dat` at ~22 s, translated does not.
- The 22 s verdict was traced to ACE starting a thread of its own and checking that its initial LR (x30) lies in a file-backed mapping with a readable `map_files` link (LOOPDEC). Translated LR was the hidden berberis vdso stub page; patch 0077 (guest-call LR in libc, hook follows the stub libc's `b` + `blr`) fixes that check (VM then follows native for 1364+ tokens, CHAIN) but not the outcome.
- Fixed fidelity gaps, all default-off and unpushed: map_files = served maps (0075/0076, `BERBERIS_MAPFILES_CONSISTENT`), r-xp library lines (0074), real arm64 `[vdso]` + `__kernel_rt_sigreturn` handler LR (0090, branch pgr-ctxaudit; the vdso module is not buildable with `m`, hand-linked), `APKLAYER_APK_PATHS=host` made complete (branch pgr-hostpaths). None of them stops the storm on pgrshared (SWEEP: 14 of 14 valid runs storm at 30-35 s: 0077b, +MFC, +MAPS_VIEW=arm64, +0090 vdso, +host paths, +SIGFRAME=kernel, stock).
- Measurement lessons: the storm is not deterministic on fresh account-free instances (storm or no storm varies by day and run; Unity never loads there: the Notice dialog comes before Unity); the reliable detector is the owner's pgrshared (consent accepted, Unity loads): storm at ~30 s in 21 of 22 runs. Stock `getenv()` in libberberis never sees the app env: use HostGetenv. A run counts only if Unity loaded, no fatal signal, no GPU errors in `journalctl -k -b` (the tester's NVIDIA driver faulted once at 08:51 and the box rebooted at 09:43: all runs in between were invalid).
- Ruled out in this round: maps text/format, r-xp bits, APK zip_open, JIT self-test (RWXTEST), path spelling (ACE's own), tids/cgroup, syscall latency, file counts, fd table, install path tokens, signature/installer/debuggable (STRINGS: signature, version, base.apk identical; installer null on both routes).
- Open: ACE's network stage at ~30 s (pgrshared) / ~86 s (fresh) frees the same 64 blocks again (VM pc 0x32824); native runs a small task at 0x33a54. Candidates still open: `dl_iterate_phdr` (9 libs vs 285 native) and `dladdr` names vs maps (agent DLPHDR), the 254 decrypted VM strings (branch pgr-strings, tools/ace/vmstrings).
