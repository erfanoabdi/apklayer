### Running the GPU route (device-library flavor), 2026-10-27
On the arm64 VM: `XDG_RUNTIME_DIR=/run/user/1000 APKLAYER_NATIVE=~/arm64-native ~/apklayer/bin/apklayer run <installed package>`; `bin/apklayer stop` ends it.
That alone starts the services (the C++ tool's stack daemon, ready marker `~/.local/state/apklayer/default/ready`), uses the arm64 JDK, and sets the environment from `scripts/native-env.sh`.
Tree-flavor install now converts against its own framework and renders metadata/icons using its arm64 runtime. Logs: `/tmp/apklayer-stack/*.log` (services), the app's stdout. `servicetool list|check|dump NAME` (btload --main) inspects services (SurfaceFlinger dump shows layers).
Capture caveat: `prlctl capture` is reliable for the GPU window now (it showed the UiBench list); Robolectric patches live in `runtime/patches/` (compiled into native-runtime.jar by `scripts/build-native-arm64.sh`).

### The C++ tool (cli/, 2026-10-28)
`bin/apklayer` execs `b/cli/apklayer` (build: `meson setup b && ninja -C b`, needs g++). Commands: `install|run|list|uninstall|stop|hub|component-host|env`, plus the test helpers `stack <lib> [args]` (services + one tool in the foreground, ends with the tool, tool output in `<logs>/tool.log`) and `exec <lib> [args]` (one library under the Android environment). Logs and markers live in `~/.local/state/apklayer/<instance>/` (`APKLAYER_LOGS` overrides). `stop` ends the stack, the hub, launched apps and the window shell and returns when they are gone. Readiness is a system property of the instance, as on Android: the daemon sets `apklayer.stack.ready=1` once SurfaceFlinger (and the audio policy service) registered (`servicetool wait`), clients block in `aprop wait apklayer.stack.ready 1` on the property store's serial futex; no timers, no marker files. `scripts/native-env.sh` and `arm64-stack.sh` are gone. Open: multi-instance (P9) is deferred.

### Vulkan G2/G3 on the UTM VM (2026-10-28): implemented, opt-in, blocked by the host stack
- `vulkan.apklayer` (Driver.cpp) implements VK_ANDROID_native_buffer over the host driver: dma-buf image import from our gralloc handles (explicit DRM layout), the memory import deferred to vkAcquireImageANDROID, acquire/release through sync-fd semaphores (an empty submission signals when there is no fence to wait for), gralloc usage queries, device creation with the host extensions that carry it. Enabled with `APKLAYER_VULKAN_PRESENT=1` only.
- Venus quirks found: `vkGetMemoryFdPropertiesKHR` aborts on a dma-buf Venus did not create (skipped, the memory type is the image's lowest); no `VK_KHR_external_fence_fd` (acquire waits the fd itself); unknown Android structs in the image chain are unlinked for the host call; allocating a gralloc buffer after a Venus import aborted (the import is deferred until all of a swapchain's buffers exist).
- Blocker: on the UTM VM (Apple M5 Max through virglrenderer/MoltenVK) Venus imports and binds a virgl dma-buf, then aborts when commands use the image; reproduced in a standalone C program with no apklayer code, and the same commands on a plain Venus image complete (control). Real presentation needs buffers allocated by Venus and bridged to the GL path, or a host whose driver can use imported dma-bufs. `tests/vm/vulkan-present.sh` shows the swapchain creating its images and stops there on this host; `tests/vm/vulkan.sh` (probe) passes on the real GPU.
