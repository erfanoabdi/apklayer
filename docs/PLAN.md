# apklayer: plan

What is decided, what is done, what comes next and what is open. Dated history: `CHANGELOG.md`; earlier plans: `docs/history/` (the full plan
before this rewrite is `docs/history/PLAN-2026-11-04-full.md`). If a decision changes, change it here in the same commit as the code.

## Decisions
| Topic | Decision |
|---|---|
| Framework | Unmodified AOSP `android-all` (the LineageOS tree's: Android 17, SDK 37) on HotSpot with Robolectric shadows. No system_server, no zygote. Upstream code (android-all, Robolectric, dex2jvm, bionic_translation, AOSP) changes only through thin patch files (`patches/`, `docs/PATCHES.md`). |
| Native side | Android's own arm64 libraries from a LineageOS 24 `gsi_arm64 userdebug` build under bionic_translation on binderfs: servicemanager, SurfaceFlinger, HWUI, media, audio, keystore2. apklayer's HALs (`aosp/hals`, `bridge/hals`) back them with GBM/EGL/Vulkan, PipeWire, GStreamer. No CPU-only route, no stand-ins. |
| Apps | dex2jvm converts DEX; one JVM per Android process, named as Android names it; per-app class loaders and linker namespaces; windows go to one per-session Wayland shell, one virtual display per app. |
| Cross-app | The instance hub (real Binder between app JVMs) implements services, broadcasts, providers, activities, notifications, pending intents, accounts, package installs, caller identity. System services stay Robolectric shadows except where a process boundary exists; system_server services are not ported into the hub (assessment in CHANGELOG 2026-11-03). |
| System apps | The tree's real providers and apps (SettingsProvider, MediaProvider, Contacts, Calendar, Downloads, DocumentsUI, WebView) installed as apklayer apps. |
| Instances | Each instance has its own binder devices, /data, /storage, app data, properties, shell session and hub (`APKLAYER_INSTANCE`). Tests run one instance per group, several at a time. |
| Readiness | Instance properties (`apklayer.stack.ready`, `apklayer.hub.ready`) waited on with `aprop wait`; no polling, no timers. |
| CLI and build | C++ CLI in `cli/`; Meson for everything (native, jars, instrumentation, install); `tools/stage`; pinned Java deps in `deps/deps.lock`, staged tree files in `deps/android-tree-files.lock`. |
| UI | `apklayer-manager` (`manager/`, Slint C++, Material 3) over the CLI's managing commands; phone and desktop layouts. |
| License | AGPL-3.0-or-later plus a paid commercial license (`COMMERCIAL.md`, audit in `docs/THIRD_PARTY.md`). |
| Hosts | arm64 Linux; x86_64 (`docs/X86_64.md`) runs on the owner's PC. Distribution: Flatpak first. |
| Verification | Every feature has a scripted check with real input and a per-instance SurfaceFlinger screenshot (`tests/run <group>`, `tests/groups.toml`); run only the groups for the code you changed. Compatibility is measured by the corpus (`tests/corpus/`) with current app versions. CTS strictly last. |
| Builds in `~/los24` | Incremental `gsi_arm64` and `gsi_x86_64 userdebug` only, never clean `out/` (`CLAUDE.md`, `docs/AOSP-BUILDS.md`). |

## Done (summary; details in CHANGELOG.md)
- **Runtime**: per-app class loaders and linker namespaces; processes carry their Android process name and run services in their declared process; Build values from the instance's property store before any app class (release identity: user/release-keys); one platform certificate per instance; a spare component host per instance (host start 1.2-1.3 s -> 0.46-0.6 s); hosts finish due work and their loopers' running work before they exit (settings survive `stop`).
- **Hub**: services, broadcasts, providers, activities, notifications, pending intents, accounts (AccountManager through the hub), package installer (sessions, preapproval, legacy intents, splits/bundles, update checks), caller identity checked against the hub's registry, system settings written at boot, audio permission feed and stream volumes for every audioserver, permission_checker for the native services.
- **System apps**: real SettingsProvider, MediaProvider, Contacts, Calendar, Downloads, UserDictionary, DocumentsUI, WebView; keystore2 with the software KeyMint (Android's AndroidKeyStore provider).
- **Graphics and windows**: our SurfaceFlinger route with dmabuf to Wayland at real vsync; EGL with Android's per-context hook tables; GLES1 through gfxstream's translator; hardware bitmaps, TextureView, SurfaceView; windows follow wp_fractional_scale_v1/wp_viewporter, first size fitted to the compositor's bounds; Adwaita-style header bar; splash until the first frame. Vulkan implemented (presentation opt-in).
- **Media and audio**: Codec2 software codecs (AVC, VP8/9, AAC, MP3, Opus...), MediaCodec into Surfaces, MediaPlayer, AudioTrack/AudioRecord/MediaRecorder through the real AudioFlinger/AudioPolicy to PipeWire; recording works.
- **Tooling**: `tests/run` (each group its own instance, UTM or Parallels, rebuilds the runtime when sources change), per-instance screenshots, scripted input into one instance's windows (`instance.inject`), corpus runner per instance, all upstream edits as patch files (bionic_translation 0001-0031, robolectric 0001-0015, aosp per project).
- **Manager**: apps (install, open, stop, clear data, uninstall, permissions with grant/revoke), instances (create, remove), properties, device info; CLI errors shown.
- **Compatibility** (tests/corpus/results.md, 2026-11-04): over 40 apps draw, among them current F-Droid versions of Feeder, Tusky, Breezy Weather, Auxio, KeePassDX, Tasks.org, Thunderbird, mpv, Organic Maps, OsmAnd, LocalSend and FluffyChat (Flutter), Standard Notes (React Native), Element, VLC, LibreTube, Material Files, Nextcloud, Shelter, GPSTest, Unciv; also Telegram, NewPipe 0.29 (lists and plays), Fennec (pages, audio), OpenTTD (GLES1), Conversations, AnkiDroid, Joplin, Lemuroid, microG.
- Latest full suite (UTM, 2026-11-04): 40 of 42 groups; vulkan-present fails on both VMs (no Vulkan presentation: needs a real GPU); native-surface's failure (kernel keys beside other instances) is fixed.

## Next phase: binary releases (decided 2026-11-04 by the owner, in progress)
State: 1-5 and 9 done (2026-11-04; v0.1.0 tagged 2026-11-04 with prebuilts-v0.1.0); v0.2.0 and v0.2.1 released the same day (0.2.0 shipped the new runtime under the old name 0.1.0: `runtime=` in tools/release/versions is bumped by hand). Done 2026-11-07: the release workflow's guard job refuses a runtime version already released from another prebuilts commit (releases.json `runtime.prebuilts`, older entries through their prebuilts-v tag; tools/release/check-runtime.py); its first tag run is untested on GitHub. 6-8 done (2026-11-04: updater with SHA256-checked deb and runtime downloads and an atomic runtime switch, first-run screen, converterAbi + `apklayer reconvert`, data-format record); the deb install path through PackageKit/pkexec is untested (no polkit agent on the VMs); the CLI must read `runtime/current` (with the packaging work).
1. **Packaging in main**: `debian/` at the repository root (no packaging branches). One `debian/control`; per-codename differences through a CI-written substvars file (`debian/<codename>.substvars`); per-codename source patches only if needed (`debian/patches/<codename>/series`, copied into place by CI). Versions from the tag: `0.1.0-1~noble1`, `0.1.0-1~trixie1`.
2. **The `apklayer` deb (per OS and CPU)**: everything glibc-linked: the CLI, the window shell, bionic_translation, the JNI shim, btload/preload, the host classes, apklayer-manager. `postinst` loads `binder_linux` (a `modules-load.d` entry; Ubuntu: depends on `linux-modules-extra`) and installs a small systemd unit that mounts binderfs and creates the default instance's devices.
3. **The Android runtime bundle** (Android libraries, Android root, framework jars: the `prebuilts` branch's content for one CPU): a release asset (zstd tarball + SHA256 manifest), the same for every Linux of that CPU; the manager downloads it into `~/.local/share/apklayer/runtime/<version>/`. Each release names the runtime version it needs.
4. **CI**: a workflow in main on `push: tags: v*`: a matrix of codename (Ubuntu noble, later releases; Debian trixie) x CPU (arm64 on `ubuntu-24.04-arm`, amd64 marked experimental), each in a container of that OS; `dpkg-buildpackage`; a final job makes the GitHub Release with the debs and the runtime bundle and updates `releases.json` on the `pages` branch.
5. **`pages` branch**: GitHub Pages with a one-page `index.html` (what apklayer is, install steps, links to the release) and `releases.json` (latest version, per OS/CPU deb URLs on Releases, SHA256s, runtime bundle URL and version, `converter-abi`). No binaries in git; no apt repository on Pages (apt fetches debs relative to its base URL). A hosted apt repository (openSUSE Build Service) may come later.
6. **Manager updater**: reads `releases.json` (no GitHub API rate limit), shows what is new, downloads the matching deb from Releases and installs it through PackageKit (or `pkexec apt install ./file.deb`), downloads the runtime bundle when its version changes.
7. **First run in the manager**: checks binder (explains the fix if missing), downloads the runtime (SHA256-checked), creates the default instance, installs the WebView provider and the system apps from the runtime bundle, offers microG (Services + Companion) and an F-Droid client.
8. **`converter-abi`**: a number bumped when dex2jvm, the instrumentation or the converted-class format changes; each install records the number it was converted with (`info.properties`); after an update the manager re-converts apps with an older number from their kept `base.apk` (data kept). The same pattern for app-data and instance layout changes (`data-format` with migration steps).
9. **Versions**: tags `vX.Y.Z` on main (first `v0.1.0`); the prebuilts branch tagged to match (`prebuilts-vX.Y.Z`).

**Ubuntu Touch install (2026-11-05, docs/HALIUM.md "The apt install on the phone")**: setup runs without root (binder nodes from the boot unit, the
WebView switch per instance, no pkexec); the manager follows Lomiri's scale and the CLI's default instance. Open before runtime 0.3.1 ships:
- releases.json still names runtime 0.2.1: a 0.3.x deb's `apklayer setup` without `--bundle` downloads the release's runtime, whatever version the
  package names (setup should refuse or say so when they differ); then tag (the Halium camera round's arm64 libraries are in the prebuilts and the
  lock since 2026-11-08, prebuilts 104383c2).
- Java on Ubuntu Touch: the deb depends on openjdk-21-jre-headless (about 200 MB on a 4 GB rootfs with ~540 MB free, gone with each OTA, like the
  deb itself); `apklayer setup` now says when Java 21 is missing. A JRE that setup provisions in the user's data home (as the runtime bundle) would
  make the package installable without it (`Recommends`); not decided.
- Instances other than `ut` on a phone: their nodes need root (`/etc/apklayer/instances` + `systemctl restart apklayer-binder`, the command the
  manager shows). Ubuntu Touch has polkitd and Lomiri's polkit agent but no pkexec; a polkit rule allowing active local users to start an
  `apklayer-binder@<id>.service` template (no password, ids validated by binder.sh) would let the manager do it: not built.

## Open by area (not in the next phase yet)
- **Startup**: the hub boots in 1.4 s on an idle UTM and 4-8 s when several groups and agents load it (CPU contention, not a regression; marks under -Dapklayer.perf in HubHost); an app's first hub call (REGISTER) waits for that boot and prints `waiting for the instance hub (N s)` every 2 s. Faster: fewer classes before READY (AppCDS done 2026-11-08).
- **Graphics**: hub starts over 3 s on a loaded UTM still time out gpu-window's 3 s silence check now and then; the ES1 translator reports "Android Emulator OpenGL ES Translator" as renderer; the host-ES1 path is untested; OpenTTD's SDL logs `Invalid texture` endlessly after a focus loss when desktop audio is unreachable.
- **Graphics performance** (window frame rate done 2026-11-05/07: 60 fps on UTM, Parallels and the x86 PC; numbers in CHANGELOG). Open: (b) the window sink (vdisplay) still waits for SurfaceFlinger's fence on the binder thread (0.03-0.6 ms), explicit sync needs a shell protocol change; (c) render straight into the dequeued buffer (the blit remains, without per-frame setup); (d) EGL_ANDROID_get_frame_timestamps / compositor timing are stubs in libapklayer_egl, so Swappy has no frame timestamps; (e) present fences are sync_files signaled at the hand-over to the shell, not at the real present (PRESENT_FENCE_IS_NOT_RELIABLE): a later signal needs a kernel fence the composer can signal itself (sw_sync: debugfs and root; vgem: not loaded), then the shell's wp_presentation feedback gives the time; (f) the swap trace (bpftrace probes in libgui) does not load on the PC.
- **Game performance** (OTR2 on the x86 PC, N100 + UHD, 2026-11-05): 30 fps with Swappy, 58 fps with `apklayer prop set swappy.disable 1` (GPU ~94% busy, the translated game thread ~80% of a core). Open: (c) and (d) above; bionic_translation is built -O0 (upstream's flags) and every proxied mutex/cond of translated code goes through it; Swappy's other inputs (appVsyncOffset 0, no SwappyDisplayManager: its natives are not registered) are untested.
- **OTR2 input** (fixed 2026-11-05): a portrait/landscape app on a mobile-style maximized window (the shell fits the requested shape to the output) is untested with games; the real "WHAT'S NEW" dialog is unchecked (the UTM profile shows none; same input path).
- **Windows**: xdg-decoration on non-GNOME desktops; a real-session scale switch check.
- **Storage**: which volumes ordinary apps (not DocumentsUI) reach through the file APIs; files carry no SELinux label (getfilecon ENODATA).
- **Input**: Back in a WebView text selection finishes the activity. Android's framework ends only a primary action mode on Back (ActionModeController); a floating one is its view's (TextView: Editor's onKeyPreIme / OnBackInvokedCallback), so this is the real Chromium's handling, which the ViewRootImpl pipeline here gives the key first: needs a device check before anything changes.
- **First start**: the `boot settings not written: NullPointerException` seen once on a fresh data home did not reproduce in 7 fresh starts (group first-start); the hub logs its stack if it comes back.
- **Releases**: the amd64 leg untested; the first command after install blocks ~75 s for the per-user runtime setup (the manager's first run must show it); a first app launch on a fresh data home once sat 20 s in the native loader (not reproduced); the manager's installed paths need a human check.
- **Calls**: needs a human check: a Meet call end to end after reconvert; writes through `array()` on an app's direct buffer are lost (needs pinned arrays); only the default-route interface is listed as a network.
- **Tests**: one tests/run per VM tree at a time (a lock refuses a second: the push and runtime rebuild replace files under running groups); an installer run once hung after its self update with `apklayer hub`, `apklayer wait hub` and the restoring `install -d` waiting on `apklayer.stack.ready` with no stack (2026-11-08, not reproduced).
- **Manager**: apps installed before 2026-11-04 need a reinstall before their permissions show; a grant reaches the app's own check at its next start; signature grants approximated from the build's allow-lists; ui.sh has no permission step; binder devices of a removed instance stay until reboot.
- **Call audio** (setMode, communication device, mic mute, device callbacks done 2026-11-08): other apps' mode and communication-device listeners are not told of a change made by another app (each app's own are); ACTION_MICROPHONE_MUTE_CHANGED is not broadcast; the mode owner is the newest requester (AudioService also weighs which requester plays).
- **Keystore** (attestation, KeyInfo, auth-bound keys with the software Gatekeeper done 2026-11-08): no per-operation authentication (timeout 0 keys, BiometricPrompt, createConfirmDeviceCredentialIntent) and no locked state while the desktop session runs (HubLockScreen: the instance is unlocked at hub and app starts); without the sandbox all app JVMs share one Linux uid, so the instance credential and gatekeeperd's permission checks (the allow-all native permission service) do not stand against an app's native code; UNLOCKED_DEVICE_REQUIRED keys untested; the gatekeeper libraries are in android-libs.list but not yet in the prebuilts, the lock or the x86_64 build.
- **libcore on HotSpot** (JdkScan leads left): SharedMemory runs on Robolectric's ShadowSharedMemory (a temp file per create), so its libcore `DirectByteBuffer(int,long,FileDescriptor,Runnable,boolean)` is never reached, but a SharedMemory received from another process cannot be mapped ("Cannot find the backing file"): a real map (Os.mmap is real) needs a shadow building the buffer through the JDK's mapped-buffer constructor. `sun.misc.Cleaner`: JDK 9+ has none (jdk.unsupported's sun.misc lacks it, and java.base cannot define that package), and a direct buffer's cleaner is a `jdk.internal.ref.Cleaner`, so a checkcast to it cannot pass without rewriting the caller; app code that frees buffers this way (old Netty/Guava-era code) uses reflection with a fallback, so it is left until an app needs it (then: a dex2jvm repoint of `sun/misc/Cleaner` to a host class).
- **Services**: webview-input failed once under 4-way load (passes alone and on reruns).
- **microG**: Google apps need microG Companion (com.android.vending) beside Services in the instance (Meet works with both: account and contacts load; it logs a Play services version mismatch, as on a phone). DroidGuard answers only with device registration on (microG's setting); text committed through test input reaches the sign-in page's input check only after a real key press.
- **Shared libraries** (`HostSharedLibraries`, `HostAppLibraries`): the build's `<library>` jars are given only when the runtime carries them as JVM classes (org.apache.http.legacy, android.test.base/mock/runner); libraries of installed apps give their classes only, not their resources; uninstalling a provider an app uses is not refused; not handled: `<uses-native-library>` (never checked), ApplicationInfo.sharedLibraryInfos, the hub's ApplicationInfo of other packages (no sharedLibraryFiles there), HIDL libraries for old system apps (dropped for every app). A known library without classes in the runtime only warns at install; com.android.location.provider, javax.obex, com.android.future.usb.accessory, com.android.media.remotedisplay, com.android.mediadrm.signer and com.android.nfc_extras are in that state (stage their `.impl` javac jars as tools/stage root does for http legacy when an app needs one).
- **Stale data paths**: apps that stored an absolute data path before 2026-11-05 (AppEnvironment.stableDataPath) keep a path into an old Robolectric temp dir; JW Library then stays on its splash screen until `apklayer clear-data`. No general fix: the old path names a per-run random directory (`<state>/tmp/robolectric-apklayer<random>/<package>-dataDir`) that each stack stop removed, and only the app's own files name it.
- **Apps**: Godot 4 needs Vulkan presentation; Meet's Google sign-in through microG needs a human check; JW Library 15.0.2 (works end to end, 2026-11-05): most cover thumbnails in the book lists stay blank; Amaze counts 8 folders for 4.

## Plan: hardware providers (decided 2026-11-04 by the owner; (a)-(e) done 2026-11-04/05, open work in item 6)

## Plan: GPU per instance (decided 2026-11-04 by the owner; mostly done 2026-11-04)

On machines with several GPUs (e.g. Intel + AMD, or a laptop's iGPU + dGPU) each instance runs on the GPU the user picks.
1. **Mechanism**: the graphics HAL already opens `$APKLAYER_RENDER_NODE` (else the first `/dev/dri/renderD*`: bridge/hals/graphics/graphics.c). The stack sets it per instance from the instance's choice, and the same choice reaches everything that selects a GPU on its own: EGL (EGL_EXT_device_enumeration / the platform device matching that node, so the GL driver is the same GPU as the allocator), Vulkan (`MESA_VK_DEVICE_SELECT=<vendor:device>`, or the loader's device order), and the media codecs (VA-API's DRM device).
2. **Stable identity**: the choice is stored by PCI path (`/dev/dri/by-path/pci-...-render`) or vendor:device + PCI slot, not by `renderD128` (the number changes between boots or after hotplug). `apklayer gpus` lists them (name from the DRM driver / PCI ids, vendor:device, node, by-path, whether the compositor runs on it).
3. **Display on another GPU**: buffers rendered on GPU B are shown by a compositor on GPU A. The HWC asks the compositor for its dmabuf feedback (linux-dmabuf v4: main device and accepted formats/modifiers per tranche) and allocates scan-out-able buffers it can import: on another GPU that usually means LINEAR (or a modifier both support); otherwise the HWC copies into a buffer allocated on the compositor's GPU (a PRIME-style blit). Measured: frame time and copies per frame.
4. **Configuration and UI**: per instance in its configuration (with the hardware providers' `providers.toml` when that exists: domain `gpu`), default "same GPU as the desktop"; the manager's instance page has a GPU dropdown filled from `apklayer gpus`; changing it restarts that instance's stack.
5. **Tests**: on a machine with two render nodes (the owner's x86 PC has one: test with a second virtual node such as vgem/vkms or on hardware with two GPUs), an instance on each GPU, the gpu and gpu-window groups pass on both, screenshots, and `GL_RENDERER`/Vulkan deviceName in the app match the chosen GPU.

3. **Storage (the owner's choice)**: default is brokered access, Android's and Flatpak's model: an app reaches the user's files only through the picker (DocumentsUI or the desktop's file chooser portal), which runs as the user and hands over the one file or folder chosen. 4. **To solve**: desktop sockets in `/run/user/<uid>` are 0700 (Wayland, PipeWire, D-Bus): apklayerd and the window shell (running as the user) open them and pass descriptors to app processes (the shell already brokers each app's window); GPU render nodes through the `render` group or the namespace mapping; per-uid ownership of app data, with a migration of existing `app-data`; Robolectric's sandbox and the component hosts per uid (one JVM per app process already).
5. **Tests**: an app cannot read another app's data dir or the user's home; a granted file is readable, a non-granted one is not; binder caller uid equals the app's uid; all groups pass with the sandbox on.

## Plan: background push (owner's task 2026-11-05; steps 1-5 done 2026-11-05, group `push`)
Goal: a messenger registered with microG's cloud messaging shows a desktop notification for a new message while its app is closed.
1. **Always-on instance** (done): `apklayer instance autostart <id> on [--no-start]|off` (cli/autostart.cpp) writes the marker `<state dir>/autostart` and a systemd user unit template `~/.config/systemd/user/apklayer-instance@.service` (`apklayer --instance %i hub` in the foreground: it brings the stack up and runs the hub; SIGTERM counts as success, a crash restarts it; `ExecStopPost` ends the stack) and enables it, so the instance starts at login. `HubDirectory.alwaysOn()` (the marker) keeps the hub from exiting when idle; so does a started service (`HubStartedServices.any()`). `instances` has a fifth column (always on); the manager's Instances page has a switch per instance.
2. **Boot broadcasts** (done): `HubBootBroadcasts` sends ACTION_LOCKED_BOOT_COMPLETED (direct-boot-aware receivers only) then ACTION_BOOT_COMPLETED once per stack start (marker `boot_completed` in the stack's runtime dir, which is new per stack), as UserController does (NO_ABORT, INCLUDE_BACKGROUND, EXTRA_USER_HANDLE, receivers need RECEIVE_BOOT_COMPLETED); closed apps with a receiver are started. Decision: only for an always-on instance (an on-demand instance starts when one app needs it; waking every app with a boot receiver, each its own JVM, for that cost more than it gives); `APKLAYER_BOOT_BROADCASTS=0` switches it off (tests).
3. **Hub stays up** (done): never while the instance is always-on or a started service exists. Finding: even in an on-demand instance the hub did not exit within 40 s of its last app on UTM (no `idle, exiting` in any hub log on the VM; the cause was not investigated, a provider host such as the settings provider's probably counts as busy), so the idle exit rarely happens in practice and the contrast could not be tested; the always-on marker makes the behaviour a decision instead of an accident.
4. **Alarms and jobs held by the hub** (done): `HubScheduler`: AlarmManager PendingIntent alarms (`set`, `setRepeating`, `setExact`..., through robolectric patch 0020 and `HostAlarms`; the hub's own PendingIntent record is the operation) and JobScheduler jobs (`HostJobs` plans in the hub) are recorded in the hub; when due the hub starts the app's process and sends the PendingIntent (AlarmManagerService: repeat interval at least 60 s, EXTRA_ALARM_COUNT as a fill-in, which an IMMUTABLE PendingIntent drops as on Android) or has the app run the job (`ENDPOINT_JOB`, HostJobs). Not modelled: exact-alarm rules (ShadowHostAlarmManager keeps canScheduleExactAlarms), Doze, job constraints, persistence across hub restarts (a PendingIntent record is in memory too), `OnAlarmListener` alarms (stay in the process), `AlarmManager.getNextAlarmClock`. A hub that is not always-on can still end with pending alarms (as before: they lived in the process). Asynchronous jobs (2026-11-05): the real JobService.jobFinished reaches HostJobs (ShadowHostJobService), from any thread; a job that asks to be rescheduled waits its backoff (linear or exponential, 10 s to 5 h), a job whose onStartJob returns false ends at once; hello-system `asyncjobs`. Open: a real WorkManager app doing one-time work (not tried; AntennaPod only schedules 12 h periodic work at start), JobWorkItem queues (`dequeueWork` gives none), onStopJob (HostJobs never stops a job), the backoff count is lost when the app process ends (the hub holds only the delay).
5. **Tests** (done): group `push` (tests/vm/push.py; apps hello-push and hello-pushgms, which delivers `com.google.android.c2dm.intent.RECEIVE` as microG's McsService does: an ordered broadcast to the app's package; the receiver is protected by `com.google.android.c2dm.permission.SEND` as Firebase's): phases push (closed app wakes, the hub's desktop popup id is non-zero), alarm and job (set by an app that is then closed, fired into a new process), boot (LOCKED then BOOT once per stack), autostart (marker, unit, instances row).
6. **Needs a human check**: a real WhatsApp or Telegram account with microG (Services + Companion, GCM registered) in an always-on instance on Parallels (`apklayer --instance <own> instance autostart <own> on`, log out and in once, or `systemctl --user start apklayer-instance@<own>`), the app closed, a message sent from another phone: a desktop notification should appear within seconds. Also check that microG's own push connection (McsService, a started service) survives with no app open, and that the unit really starts the stack at login (the test only checks the unit and the marker: `systemctl --user` behaves differently under the test runner's XDG_RUNTIME_DIR). Open: the boot broadcast wakes every app with a boot receiver at once (each a JVM: memory on small machines); a data-saving rule for them is not designed.
