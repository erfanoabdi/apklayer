# apklayer: plan

What is decided, what is done, what comes next and what is open. Dated history: `CHANGELOG.md`; earlier plans: `docs/history/` (the full plan
before this rewrite is `docs/history/PLAN-2026-11-04-full.md`). If a decision changes, change it here in the same commit as the code.

## Decisions
| Topic | Decision |
|---|---|
| Framework | Unmodified AOSP `android-all` (the LineageOS tree's: Android 17, SDK 37) on HotSpot with Robolectric shadows. No system_server, no zygote. Upstream code (android-all, Robolectric, dex2jvm, bionic_translation, AOSP) changes only through thin patch files (`patches/`, `docs/PATCHES.md`). |
| Native side | Android's own arm64 libraries from a LineageOS 24 `gsi_arm64 userdebug` build under bionic_translation on binderfs: servicemanager, SurfaceFlinger, HWUI, media, audio, keystore2. apklayer's HALs (`aosp/hals`, `bridge/hals`) back them with GBM/EGL/Vulkan, PipeWire, GStreamer. No CPU-only route, no stand-ins. |
| Apps | dex2jvm converts DEX; one JVM per Android process, named as Android names it; per-app class loaders and linker namespaces; windows go to one per-session Wayland shell, one virtual display per app. |
| Cross-app | The instance hub (real Binder between app JVMs) implements services, broadcasts, providers, activities, notifications, pending intents, accounts, package installs, caller identity. System services stay Robolectric shadows except where a process boundary exists; system_server services are not ported into the hub (assessment in CHANGELOG 2026-11-03). |
| System apps | The tree's real providers and apps (SettingsProvider, MediaProvider, Contacts, Calendar, Downloads, DocumentsUI, WebView) installed as apklayer apps. |
| Instances | Each instance has its own binder devices, /data, /storage, app data, properties, shell session and hub (`APKLAYER_INSTANCE`). Tests run one instance per group, several at a time. |
| Readiness | Instance properties (`apklayer.stack.ready`, `apklayer.hub.ready`) waited on with `aprop wait`; no polling, no timers. |
| CLI and build | C++ CLI in `cli/`; Meson for native code; `tools/build`, `tools/stage`; pinned Java deps in `deps/deps.lock`, staged tree files in `deps/android-tree-files.lock`. |
| UI | `apklayer-manager` (`manager/`, Slint C++, Material 3) over the CLI's managing commands; phone and desktop layouts. |
| License | AGPL-3.0-or-later plus a paid commercial license (`COMMERCIAL.md`, audit in `docs/THIRD_PARTY.md`). |
| Hosts | arm64 Linux today; x86_64 staged (`docs/X86_64.md`), never run on hardware. Distribution: Flatpak first. |
| Verification | Every feature has a scripted check with real input and a per-instance SurfaceFlinger screenshot (`tests/run <group>`, `tests/groups.toml`); run only the groups for the code you changed. Compatibility is measured by the corpus (`tests/corpus/`) with current app versions. CTS strictly last. |
| Builds in `~/los24` | Incremental `gsi_arm64 userdebug` only, never clean `out/` (`CLAUDE.md`, `docs/AOSP-BUILDS.md`). |

## Done (summary; details in CHANGELOG.md)
- **Runtime**: per-app class loaders and linker namespaces; processes carry their Android process name and run services in their declared process; Build values from the instance's property store before any app class (release identity: user/release-keys); one platform certificate per instance; a spare component host per instance (host start 1.2-1.3 s -> 0.46-0.6 s); hosts finish due work and their loopers' running work before they exit (settings survive `stop`).
- **Hub**: services, broadcasts, providers, activities, notifications, pending intents, accounts (AccountManager through the hub), package installer (sessions, preapproval, legacy intents, splits/bundles, update checks), caller identity checked against the hub's registry, system settings written at boot, audio permission feed and stream volumes for every audioserver, permission_checker for the native services.
- **System apps**: real SettingsProvider, MediaProvider, Contacts, Calendar, Downloads, UserDictionary, DocumentsUI, WebView; keystore2 with the software KeyMint (Android's AndroidKeyStore provider).
- **Graphics and windows**: our SurfaceFlinger route with dmabuf to Wayland at real vsync; EGL with Android's per-context hook tables; GLES1 through gfxstream's translator; hardware bitmaps, TextureView, SurfaceView; windows follow wp_fractional_scale_v1/wp_viewporter, first size fitted to the compositor's bounds; Adwaita-style header bar; splash until the first frame. Vulkan implemented (presentation opt-in).
- **Media and audio**: Codec2 software codecs (AVC, VP8/9, AAC, MP3, Opus...), MediaCodec into Surfaces, MediaPlayer, AudioTrack/AudioRecord/MediaRecorder through the real AudioFlinger/AudioPolicy to PipeWire; recording works.
- **Tooling**: `tests/run` (each group its own instance, UTM or Parallels, rebuilds the runtime when sources change), per-instance screenshots, scripted input into one instance's windows (`instance.inject`), corpus runner per instance, all upstream edits as patch files (bionic_translation 0001-0031, robolectric 0001-0015, aosp per project).
- **Manager**: apps (install, open, stop, clear data, uninstall, permissions with grant/revoke), instances (create, remove), properties, device info; CLI errors shown.
- **Compatibility** (tests/corpus/results.md, 2026-11-04): over 40 apps draw, among them current F-Droid versions of Feeder, Tusky, Breezy Weather, Auxio, KeePassDX, Tasks.org, Thunderbird, mpv, Organic Maps, OsmAnd, LocalSend and FluffyChat (Flutter), Standard Notes (React Native), Element, VLC, LibreTube, Material Files, Nextcloud, Shelter, GPSTest, Unciv; also Telegram, NewPipe 0.29 (lists and plays), Fennec (pages, audio), OpenTTD (GLES1), Conversations, AnkiDroid, Joplin, Lemuroid, microG.
- Latest full suite (UTM, 2026-11-04): 40 of 42 groups; vulkan-present fails on both VMs (no Vulkan presentation: needs a real GPU); native-surface's failure (kernel keys beside other instances) is fixed.

## Next phase: binary releases (decided 2026-11-04 by the owner, in progress)
State: 1-5 and 9 done (2026-11-04; first real tag pending), 6-8 done (2026-11-04: updater with SHA256-checked deb and runtime downloads and an atomic runtime switch, first-run screen, converterAbi + `apklayer reconvert`, data-format record); the deb install path through PackageKit/pkexec is untested (no polkit agent on the VMs); the CLI must read `runtime/current` (with the packaging work).
1. **Packaging in main**: `debian/` at the repository root (no packaging branches). One `debian/control`; per-codename differences through a CI-written substvars file (`debian/<codename>.substvars`); per-codename source patches only if needed (`debian/patches/<codename>/series`, copied into place by CI). Versions from the tag: `0.1.0-1~noble1`, `0.1.0-1~trixie1`.
2. **The `apklayer` deb (per OS and CPU)**: everything glibc-linked: the CLI, the window shell, bionic_translation, the JNI shim, btload/preload, the host classes, apklayer-manager. `postinst` loads `binder_linux` (a `modules-load.d` entry; Ubuntu: depends on `linux-modules-extra`) and installs a small systemd unit that mounts binderfs and creates the default instance's devices.
3. **The Android runtime bundle** (Android libraries, Android root, framework jars: the `prebuilts` branch's content for one CPU): a release asset (zstd tarball + SHA256 manifest), the same for every Linux of that CPU; the manager downloads it into `~/.local/share/apklayer/runtime/<version>/`. Each release names the runtime version it needs.
4. **CI**: a workflow in main on `push: tags: v*`: a matrix of codename (Ubuntu noble, later releases; Debian trixie) x CPU (arm64 on `ubuntu-24.04-arm`, amd64 marked experimental), each in a container of that OS; `dpkg-buildpackage`; a final job makes the GitHub Release with the debs and the runtime bundle and updates `releases.json` on the `pages` branch.
5. **`pages` branch**: GitHub Pages with a one-page `index.html` (what apklayer is, install steps, links to the release) and `releases.json` (latest version, per OS/CPU deb URLs on Releases, SHA256s, runtime bundle URL and version, `converter-abi`). No binaries in git; no apt repository on Pages (apt fetches debs relative to its base URL). A hosted apt repository (openSUSE Build Service) may come later.
6. **Manager updater**: reads `releases.json` (no GitHub API rate limit), shows what is new, downloads the matching deb from Releases and installs it through PackageKit (or `pkexec apt install ./file.deb`), downloads the runtime bundle when its version changes.
7. **First run in the manager**: checks binder (explains the fix if missing), downloads the runtime (SHA256-checked), creates the default instance, installs the WebView provider and the system apps from the runtime bundle, offers microG (Services + Companion) and an F-Droid client.
8. **`converter-abi`**: a number bumped when dex2jvm, the instrumentation or the converted-class format changes; each install records the number it was converted with (`info.properties`); after an update the manager re-converts apps with an older number from their kept `base.apk` (data kept). The same pattern for app-data and instance layout changes (`data-format` with migration steps).
9. **Versions**: tags `vX.Y.Z` on main (first `v0.1.0`); the prebuilts branch tagged to match (`prebuilts-vX.Y.Z`).

## Plan: hardware providers (decided 2026-11-04 by the owner, not started)
**Principle**: Android's own HAL interfaces (AIDL or HIDL, as the framework expects them) are the only interface: no apklayer-specific front. Per domain a *provider* serves that interface; a per-instance configuration picks it.
1. **Providers**: *device* (the real device's HAL on Halium/Sailfish, through the host binder contexts below); *apklayer* (our implementations of the standard interfaces, the fronts we have today, with plugin backends); *fake* (fixed or scripted values from the manager; tests).
2. **Device HALs through host binder contexts** (Waydroid's approach, thin patches in `patches/aosp/`): libbinder gets a host context for AIDL (`/dev/host_binder` style, Waydroid frameworks/native 0015: ProcessState/IPCThreadState per context, BpBinder remembers its context, IServiceManager falls back to the host servicemanager for names not served locally); libhwbinder/libhidl the same for HIDL (`host_hwbinder`, Waydroid libhwbinder 0001/0002, libhidl 0001-0008: the host-HAL allow-list, vendor passthrough paths). Host HALs see our processes as the host uid (Waydroid frameworks/native 0009). Version differences: the framework's own compatibility support (Treble); no version adapters. apklayer opens the device's binder devices from outside the Halium container as Waydroid does. The allow-list is generated from the provider choice (a domain set to "device" is listed and its apklayer front not started). Passthrough HALs and vendor libraries (gralloc mapper, the GPU driver behind EGL) load through bionic_translation's linker in the vendor (sphal) namespace.
3. **apklayer providers on desktops and non-Halium devices**: the fronts are apklayer's implementations of the standard interfaces (as today: allocator, composer3, audio core, Codec2; next: sensors, GNSS, vibrator, camera provider), with backends behind them as plugins: `libapklayer-<domain>-<backend>.so`, a small C ABI (as `bridge/hals` is), `probe()` reporting availability and quality; the best available is the default.
   - Sensors: fake, iio-sensor-proxy (D-Bus), sensorfw (as waydroid-sensors), Qt Sensors.
   - Location (GNSS): fake (fixed point, GPX replay), GeoClue, Ubuntu Touch platform-api, Qt Positioning, gpsd.
   - Camera: fake (video file or still image), PipeWire / camera portal (libcamera), V4L2.
   - Vibrator: fake, feedbackd, Linux force-feedback input devices, sysfs LED/timed_output.
   - Audio: PipeWire (today), PulseAudio. Media codecs: Codec2 software (today), GStreamer/VA-API.
   - Telephony: none (today), ModemManager, oFono. Battery: UPower. Network: NetworkManager. Bluetooth: BlueZ.
4. **Graphics**: apklayer's own HWC (composer3, windows on Wayland) on every host, devices included; the device's hwcomposer is never used. Allocator, mapper and GPU drivers come from the provider (GBM/EGL on desktops; the device's gralloc and EGL on Halium). The HWC hands buffers to the compositor through linux-dmabuf (`zwp_linux_dmabuf_v1`) on desktops, and through libhybris's `android_wlegl` protocol on Halium (`create_handle`/`create_buffer`: the gralloc native_handle's fds and ints, wrapped as a `wl_buffer` by Lomiri/Mir or Lipstick; there is no dmabuf there; reference: Waydroid's `android_hardware_waydroid/hwcomposer/wayland-android.xml`). Chosen by what the compositor advertises.
5. **Configuration and UI**: per instance `<instance root>/providers.toml` (domain -> provider and backend, backend options such as a fake location or a video file); the stack starts the configured services; a change restarts only that domain's service. Manager: a Hardware page, one row per domain (provider/backend dropdown filled from `probe()`, options, live test values for fake providers).
6. **Tests**: every backend through its Android interface from a test app (sensor events at a set rate, a location fix, a vibration pattern, camera frames); fake providers make each group deterministic. The host-context path on the VMs: a second instance plays "the device" and registers HALs on its binder devices; the first reaches them through the host context. A real Halium/Sailfish device check goes under "Needs real hardware".
7. **Order**: (a) fake providers for sensors, GNSS, vibrator and camera behind the existing fronts, with the provider config and tests; (b) the manager Hardware page; (c) real backends (iio, sensorfw, GeoClue, feedbackd, PipeWire camera); (d) the host binder contexts (AIDL, HIDL) with the two-instance test; (e) the Halium graphics path (device gralloc, `android_wlegl`).
8. **Parked**: a userspace binder transport (RPC binder over Unix sockets as a fallback for hosts without binder_linux and for Flatpak): revisit later.

## Plan: GPU per instance (decided 2026-11-04 by the owner, not started)
On machines with several GPUs (e.g. Intel + AMD, or a laptop's iGPU + dGPU) each instance runs on the GPU the user picks.
1. **Mechanism**: the graphics HAL already opens `$APKLAYER_RENDER_NODE` (else the first `/dev/dri/renderD*`: bridge/hals/graphics/graphics.c). The stack sets it per instance from the instance's choice, and the same choice reaches everything that selects a GPU on its own: EGL (EGL_EXT_device_enumeration / the platform device matching that node, so the GL driver is the same GPU as the allocator), Vulkan (`MESA_VK_DEVICE_SELECT=<vendor:device>`, or the loader's device order), and the media codecs (VA-API's DRM device).
2. **Stable identity**: the choice is stored by PCI path (`/dev/dri/by-path/pci-...-render`) or vendor:device + PCI slot, not by `renderD128` (the number changes between boots or after hotplug). `apklayer gpus` lists them (name from the DRM driver / PCI ids, vendor:device, node, by-path, whether the compositor runs on it).
3. **Display on another GPU**: buffers rendered on GPU B are shown by a compositor on GPU A. The HWC asks the compositor for its dmabuf feedback (linux-dmabuf v4: main device and accepted formats/modifiers per tranche) and allocates scan-out-able buffers it can import: on another GPU that usually means LINEAR (or a modifier both support); otherwise the HWC copies into a buffer allocated on the compositor's GPU (a PRIME-style blit). Measured: frame time and copies per frame.
4. **Configuration and UI**: per instance in its configuration (with the hardware providers' `providers.toml` when that exists: domain `gpu`), default "same GPU as the desktop"; the manager's instance page has a GPU dropdown filled from `apklayer gpus`; changing it restarts that instance's stack.
5. **Tests**: on a machine with two render nodes (the owner's x86 PC has one: test with a second virtual node such as vgem/vkms or on hardware with two GPUs), an instance on each GPU, the gpu and gpu-window groups pass on both, screenshots, and `GL_RENDERER`/Vulkan deviceName in the app match the chosen GPU.

## Plan: apps built for another CPU (decided 2026-11-04 by the owner, not started)
Apps whose native libraries exist only for another CPU: arm64-only apps on x86_64 hosts, and arm32-only (armeabi-v7a) apps on arm64 or x86_64 hosts.
1. **arm64 apps on x86_64 hosts: Digitalis** (https://digitalisx64.github.io): an ARM64 guest backend for AOSP's Berberis translator, exposed through Android's NativeBridge interface (`NativeBridgeCallbacks`: `loadLibrary`, `getTrampoline`, namespaces), JIT with a translation cache.
   - Wiring: apklayer's NativeLoader (runtime/host/.../NativeLoader*, bridge/native/native_loader.c) checks an app's ABIs at install (`lib/<abi>/`): no host ABI but arm64 present -> the app runs with the native bridge; `System.loadLibrary` and JNI calls go through the bridge's trampolines, as libnativebridge does on Android (`ro.dalvik.vm.native.bridge`, `ro.enable.native.bridge.exec`).
   - Guest libraries: translated code links against arm64 Android libraries (bionic, liblog, libGLESv2/EGL stubs that forward to the host's), which the arm64 prebuilts already have: the x86_64 runtime bundle adds them as the guest set (Berberis's guest namespace layout).
   - Build: the Berberis tree with Digitalis's arm64 guest inside the LineageOS tree (gsi_x86_64, the same incremental rules) or from Digitalis's own build guide; a patch file per change, listed in docs/PATCHES.md and docs/THIRD_PARTY.md (Apache-2.0).
   - Tests: a test app with an arm64-only JNI library (arithmetic, callbacks into Java, threads, GL) installed on the x86 PC; corpus apps that ship arm64 only; startup cost of the first translation and of a warm cache measured.
2. **arm32 apps (armeabi-v7a) on arm64 and x86_64 hosts**: a 64-bit JVM cannot load 32-bit libraries, so arm32 apps need either a 32-bit app process or translation into the 64-bit process. Recommended in this order:
   - **(a) A 32-bit app process** (Android's own answer: the 32-bit zygote): an armhf JVM (OpenJDK armhf) with armhf builds of bionic_translation, the JNI shim and btload, and the arm32 Android libraries (gsi_arm64 builds them as `system/lib/`). It speaks binder to the 64-bit stack and hub like any app process (binder is 32/64-bit compatible). On arm64 CPUs that still run AArch32 at EL0 (many Cortex-A7x boards and phones) it runs natively, at full speed. On CPUs without AArch32 (Apple Silicon VMs, Cortex-A715 and later, Oryon) and on x86_64 hosts it runs under qemu-user through binfmt_misc: complete and standard, but slow (whole JVM emulated).
   - **(b) Later, if arm32 apps matter enough: an ARM32 guest for the same Berberis-based bridge as Digitalis**, so arm32 libraries run translated inside the 64-bit process (no emulated JVM). A large project; worth it only if (a)'s qemu speed is a problem in practice.
   - Not chosen: libndk_translation and Houdini (closed, not redistributable), QEMU/Unicorn inside the process (no ready Android ABI and syscall thunking), box86 (x86 hosts only, the wrong direction).
   - Context: Google Play has required 64-bit libraries since 2019, so arm32-only apps are mostly old or niche: (a) covers them with the least new code.
   - Tests: a test app with only armeabi-v7a JNI libraries; on an AArch32-capable arm64 board natively, on the VMs (no AArch32 on Apple Silicon) and the x86 PC through qemu-user; corpus apps that ship arm32 only.
3. **Install and manager**: `apklayer install` records the chosen route (native, native bridge, 32-bit process) in info.properties; the manager shows it per app ("translated", "32-bit"); an app with no runnable ABI is refused at install with a clear reason.

## Plan: per-app sandbox with `apklayerd` (decided 2026-11-04 by the owner, not started)
Today every app JVM runs as the desktop user: apps can read each other's data and the user's home, and caller identity rests on the hub's pid registry.
1. **Daemon**: one rootless user daemon, `apklayerd` (`systemctl --user`), grown from today's per-instance stack daemon: it owns the instances (binder devices, stacks, hubs, spare hosts) and starts every app process. The CLI and the manager talk to it over a socket (`SO_PEERCRED` checks the caller). No root daemon (a daemon bug would be a root exploit, docker's known problem; root services also do not fit Flatpak).
2. **Per-app uids**: each app (per instance) gets its own uid inside a user namespace, mapped to the user's `/etc/subuid` range (rootless podman's model: newuidmap/newgidmap); its own mount namespace shows its `/data` and what it was granted, read-only shared runtime files, nothing of the user's home. Ubuntu 24.04+ restricts unprivileged user namespaces: ship one AppArmor profile for apklayerd. The kernel then attests binder caller uids (keystore2 namespaces, AppOps, permission checks follow the real uid).
3. **Storage (the owner's choice)**: default is brokered access, Android's and Flatpak's model: an app reaches the user's files only through the picker (DocumentsUI or the desktop's file chooser portal), which runs as the user and hands over the one file or folder chosen. Per-app opt-in in the manager: full Home access (the user's home mounted read-write into that app's view; offered for apps holding `MANAGE_EXTERNAL_STORAGE`, like Flatpak's `--filesystem=home`).
4. **To solve**: desktop sockets in `/run/user/<uid>` are 0700 (Wayland, PipeWire, D-Bus): apklayerd and the window shell (running as the user) open them and pass descriptors to app processes (the shell already brokers each app's window); GPU render nodes through the `render` group or the namespace mapping; per-uid ownership of app data, with a migration of existing `app-data`; Robolectric's sandbox and the component hosts per uid (one JVM per app process already).
5. **Tests**: an app cannot read another app's data dir or the user's home; a granted file is readable, a non-granted one is not; binder caller uid equals the app's uid; all groups pass with the sandbox on.
