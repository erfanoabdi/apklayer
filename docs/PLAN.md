# apklayer: plan

What is decided, what is done, what comes next and what is open. Dated history: `CHANGELOG.md`; earlier plans: `docs/history/` (the full plan
before this rewrite is `docs/history/PLAN-2026-11-04-full.md`). If a decision changes, change it here in the same commit as the code.

## Decisions
| Topic | Decision |
|---|---|
| Framework | Unmodified AOSP `android-all` (the LineageOS tree's: Android 17, SDK 37) on HotSpot with Robolectric shadows. No system_server, no zygote. Upstream code (android-all, Robolectric, dex2jvm, bionic_translation, AOSP) changes only through thin patch files (`patches/`, `docs/PATCHES.md`). |
| Native side | Android's own arm64 libraries from a LineageOS 24 `gsi_arm64 userdebug` build under bionic_translation on binderfs: servicemanager, SurfaceFlinger, HWUI, media, audio, keystore2. apklayer's HALs (`aosp/hals`, `bridge/hals`) back them with GBM/EGL/Vulkan, PipeWire, GStreamer. No CPU-only route, no stand-ins. |
| Apps | dex2jvm converts DEX; one JVM per Android process, named as Android names it; per-app class loaders and linker namespaces; windows go to one per-session Wayland shell, one virtual display per app. |
| Cross-app | The instance hub (real Binder between app JVMs) implements services, broadcasts, providers, activities, notifications, pending intents, accounts, package installs, caller identity. System services stay Robolectric shadows except where a process boundary exists; system_server services are not ported into the hub (assessment in CHANGELOG 2026-11-03). |
| System apps | The tree's real providers and apps (SettingsProvider, MediaProvider, Contacts, Calendar, Downloads, DocumentsUI, WebView) installed as apklayer apps. |
| Instances | Each instance has its own binder devices, /data, /storage, app data, properties, shell session and hub (`APKLAYER_INSTANCE`). Tests run one instance per group, several at a time. |
| Readiness | Instance properties (`apklayer.stack.ready`, `apklayer.hub.ready`) waited on with `aprop wait`; no polling, no timers. |
| CLI and build | C++ CLI in `cli/`; Meson for everything (native, jars, instrumentation, install); `tools/stage`; pinned Java deps in `deps/deps.lock`, staged tree files in `deps/android-tree-files.lock`. |
| UI | `apklayer-manager` (`manager/`, Slint C++, Material 3) over the CLI's managing commands; phone and desktop layouts. |
| License | AGPL-3.0-or-later plus a paid commercial license (`COMMERCIAL.md`, audit in `docs/THIRD_PARTY.md`). |
| Hosts | arm64 Linux; x86_64 (`docs/X86_64.md`) runs on the owner's PC. Distribution: Flatpak first. |
| Verification | Every feature has a scripted check with real input and a per-instance SurfaceFlinger screenshot (`tests/run <group>`, `tests/groups.toml`); run only the groups for the code you changed. Compatibility is measured by the corpus (`tests/corpus/`) with current app versions. CTS strictly last. |
| Builds in `~/los24` | Incremental `gsi_arm64` and `gsi_x86_64 userdebug` only, never clean `out/` (`CLAUDE.md`, `docs/AOSP-BUILDS.md`). |

## Done (summary; details in CHANGELOG.md)
- **Runtime**: per-app class loaders and linker namespaces; processes carry their Android process name and run services in their declared process; Build values from the instance's property store before any app class (release identity: user/release-keys); one platform certificate per instance; a spare component host per instance (host start 1.2-1.3 s -> 0.46-0.6 s); hosts finish due work and their loopers' running work before they exit (settings survive `stop`).
- **Hub**: services, broadcasts, providers, activities, notifications, pending intents, accounts (AccountManager through the hub), package installer (sessions, preapproval, legacy intents, splits/bundles, update checks), caller identity checked against the hub's registry, system settings written at boot, audio permission feed and stream volumes for every audioserver, permission_checker for the native services.
- **System apps**: real SettingsProvider, MediaProvider, Contacts, Calendar, Downloads, UserDictionary, DocumentsUI, WebView; keystore2 with the software KeyMint (Android's AndroidKeyStore provider).
- **Graphics and windows**: our SurfaceFlinger route with dmabuf to Wayland at real vsync; EGL with Android's per-context hook tables; GLES1 through gfxstream's translator; hardware bitmaps, TextureView, SurfaceView; windows follow wp_fractional_scale_v1/wp_viewporter, first size fitted to the compositor's bounds; Adwaita-style header bar; splash until the first frame. Vulkan implemented (presentation opt-in).
- **Media and audio**: Codec2 software codecs (AVC, VP8/9, AAC, MP3, Opus...), MediaCodec into Surfaces, MediaPlayer, AudioTrack/AudioRecord/MediaRecorder through the real AudioFlinger/AudioPolicy to PipeWire; recording works.
- **Tooling**: `tests/run` (each group its own instance, UTM or Parallels, rebuilds the runtime when sources change), per-instance screenshots, scripted input into one instance's windows (`instance.inject`), corpus runner per instance, all upstream edits as patch files (bionic_translation 0001-0031, robolectric 0001-0015, aosp per project).
- **Manager**: apps (install, open, stop, clear data, uninstall, permissions with grant/revoke), instances (create, remove), properties, device info; CLI errors shown.
- **Compatibility** (tests/corpus/results.md, 2026-11-04): over 40 apps draw, among them current F-Droid versions of Feeder, Tusky, Breezy Weather, Auxio, KeePassDX, Tasks.org, Thunderbird, mpv, Organic Maps, OsmAnd, LocalSend and FluffyChat (Flutter), Standard Notes (React Native), Element, VLC, LibreTube, Material Files, Nextcloud, Shelter, GPSTest, Unciv; also Telegram, NewPipe 0.29 (lists and plays), Fennec (pages, audio), OpenTTD (GLES1), Conversations, AnkiDroid, Joplin, Lemuroid, microG.
- Latest full suite (UTM, 2026-11-04): 40 of 42 groups; vulkan-present fails on both VMs (no Vulkan presentation: needs a real GPU); native-surface's failure (kernel keys beside other instances) is fixed.

## Next phase: binary releases (decided 2026-11-04 by the owner, in progress)
State: 1-5 and 9 done (2026-11-04; v0.1.0 tagged 2026-11-04 with prebuilts-v0.1.0); v0.2.0 and v0.2.1 released the same day (0.2.0 shipped the new runtime under the old name 0.1.0: `runtime=` in tools/release/versions is bumped by hand). Done 2026-11-07: the release workflow's guard job refuses a runtime version already released from another prebuilts commit (releases.json `runtime.prebuilts`, older entries through their prebuilts-v tag; tools/release/check-runtime.py); its first tag run is untested on GitHub. 6-8 done (2026-11-04: updater with SHA256-checked deb and runtime downloads and an atomic runtime switch, first-run screen, converterAbi + `apklayer reconvert`, data-format record); the deb install path through PackageKit/pkexec is untested (no polkit agent on the VMs); the CLI must read `runtime/current` (with the packaging work).
1. **Packaging in main**: `debian/` at the repository root (no packaging branches). One `debian/control`; per-codename differences through a CI-written substvars file (`debian/<codename>.substvars`); per-codename source patches only if needed (`debian/patches/<codename>/series`, copied into place by CI). Versions from the tag: `0.1.0-1~noble1`, `0.1.0-1~trixie1`.
2. **The `apklayer` deb (per OS and CPU)**: everything glibc-linked: the CLI, the window shell, bionic_translation, the JNI shim, btload/preload, the host classes, apklayer-manager. `postinst` loads `binder_linux` (a `modules-load.d` entry; Ubuntu: depends on `linux-modules-extra`) and installs a small systemd unit that mounts binderfs and creates the default instance's devices.
3. **The Android runtime bundle** (Android libraries, Android root, framework jars: the `prebuilts` branch's content for one CPU): a release asset (zstd tarball + SHA256 manifest), the same for every Linux of that CPU; the manager downloads it into `~/.local/share/apklayer/runtime/<version>/`. Each release names the runtime version it needs.
4. **CI**: a workflow in main on `push: tags: v*`: a matrix of codename (Ubuntu noble, later releases; Debian trixie) x CPU (arm64 on `ubuntu-24.04-arm`, amd64 marked experimental), each in a container of that OS; `dpkg-buildpackage`; a final job makes the GitHub Release with the debs and the runtime bundle and updates `releases.json` on the `pages` branch.
5. **`pages` branch**: GitHub Pages with a one-page `index.html` (what apklayer is, install steps, links to the release) and `releases.json` (latest version, per OS/CPU deb URLs on Releases, SHA256s, runtime bundle URL and version, `converter-abi`). No binaries in git; no apt repository on Pages (apt fetches debs relative to its base URL). A hosted apt repository (openSUSE Build Service) may come later.
6. **Manager updater**: reads `releases.json` (no GitHub API rate limit), shows what is new, downloads the matching deb from Releases and installs it through PackageKit (or `pkexec apt install ./file.deb`), downloads the runtime bundle when its version changes.
7. **First run in the manager**: checks binder (explains the fix if missing), downloads the runtime (SHA256-checked), creates the default instance, installs the WebView provider and the system apps from the runtime bundle, offers microG (Services + Companion) and an F-Droid client.
8. **`converter-abi`**: a number bumped when dex2jvm, the instrumentation or the converted-class format changes; each install records the number it was converted with (`info.properties`); after an update the manager re-converts apps with an older number from their kept `base.apk` (data kept). The same pattern for app-data and instance layout changes (`data-format` with migration steps).
9. **Versions**: tags `vX.Y.Z` on main (first `v0.1.0`); the prebuilts branch tagged to match (`prebuilts-vX.Y.Z`).

**Ubuntu Touch install (2026-11-05, docs/HALIUM.md "The apt install on the phone")**: setup runs without root (binder nodes from the boot unit, the
WebView switch per instance, no pkexec); the manager follows Lomiri's scale and the CLI's default instance. Open before runtime 0.3.1 ships:
- releases.json still names runtime 0.2.1: a 0.3.x deb's `apklayer setup` without `--bundle` downloads the release's runtime, whatever version the
  package names (setup should refuse or say so when they differ); then tag (the Halium camera round's arm64 libraries are in the prebuilts and the
  lock since 2026-11-08, prebuilts 104383c2).
- Java on Ubuntu Touch: the deb depends on openjdk-21-jre-headless (about 200 MB on a 4 GB rootfs with ~540 MB free, gone with each OTA, like the
  deb itself); `apklayer setup` now says when Java 21 is missing. A JRE that setup provisions in the user's data home (as the runtime bundle) would
  make the package installable without it (`Recommends`); not decided.
- Instances other than `ut` on a phone: their nodes need root (`/etc/apklayer/instances` + `systemctl restart apklayer-binder`, the command the
  manager shows). Ubuntu Touch has polkitd and Lomiri's polkit agent but no pkexec; a polkit rule allowing active local users to start an
  `apklayer-binder@<id>.service` template (no password, ids validated by binder.sh) would let the manager do it: not built.

On machines with several GPUs (e.g. Intel + AMD, or a laptop's iGPU + dGPU) each instance runs on the GPU the user picks.
1. **Mechanism**: the graphics HAL already opens `$APKLAYER_RENDER_NODE` (else the first `/dev/dri/renderD*`: bridge/hals/graphics/graphics.c). The stack sets it per instance from the instance's choice, and the same choice reaches everything that selects a GPU on its own: EGL (EGL_EXT_device_enumeration / the platform device matching that node, so the GL driver is the same GPU as the allocator), Vulkan (`MESA_VK_DEVICE_SELECT=<vendor:device>`, or the loader's device order), and the media codecs (VA-API's DRM device).
2. **Stable identity**: the choice is stored by PCI path (`/dev/dri/by-path/pci-...-render`) or vendor:device + PCI slot, not by `renderD128` (the number changes between boots or after hotplug). `apklayer gpus` lists them (name from the DRM driver / PCI ids, vendor:device, node, by-path, whether the compositor runs on it).
3. **Display on another GPU**: buffers rendered on GPU B are shown by a compositor on GPU A. The HWC asks the compositor for its dmabuf feedback (linux-dmabuf v4: main device and accepted formats/modifiers per tranche) and allocates scan-out-able buffers it can import: on another GPU that usually means LINEAR (or a modifier both support); otherwise the HWC copies into a buffer allocated on the compositor's GPU (a PRIME-style blit). Measured: frame time and copies per frame.
4. **Configuration and UI**: per instance in its configuration (with the hardware providers' `providers.toml` when that exists: domain `gpu`), default "same GPU as the desktop"; the manager's instance page has a GPU dropdown filled from `apklayer gpus`; changing it restarts that instance's stack.

## Plan: binder in userspace, no kernel binder (owner's direction 2026-11-08; the default since 0.4.9, owner 2026-11-09)
Goal: apklayer needs no kernel binder at all (no binder_linux module, no binderfs mount, no root setup step, no per-instance devices that stay
until reboot, no Flatpak host step). Halium phones keep talking to the *device's own* HALs (camera, vibrator) over the phone's kernel binder;
that is the device's binder, not apklayer's.

Options looked at (2026-11-08):
- **RPC binder** (libbinder `RpcServer`/`RpcSession`, Android 12+, over Unix sockets/vsock/TCP; used by AVF/microdroid; fd passing over Unix
  sockets since 13). Not a whole-system replacement: a binder received over one session cannot be passed to a third process over another
  (Android's framework passes binders between processes all the time: the hub hands an app another app's binder; SurfaceFlinger, audio and
  BLASTBufferQueue pass tokens), servicemanager hands out RPC binders only through Android 16's accessors, and every service would need
  patching to serve both ways. Useful only for fixed point-to-point links.
- **Innkeeper** (github.com/sargunv/innkeeper, Rust, AGPL-3.0, started 2026-10-27, pre-alpha): runs unmodified AOSP in Flatpak; a "broker"
  parent process puts Android's init under a seccomp user-notification filter that traps `openat(/dev/*binder)` and binder ioctls and serves
  them: a 4 MiB memfd injected as the receive area (`SECCOMP_IOCTL_NOTIF_ADDFD`), caller memory through `/proc/<pid>/mem`, a driver model
  (`supervisor/broker/src/binder/driver.rs`) that follows `drivers/android/binder.c` and is unit-tested; one broker thread, 70-90k
  transactions/s, 15 us round trip against 3.8 us for kernel binder; no priority inheritance, fds can leak when a transaction fails after some
  were installed; `sender_euid` is a virtual uid (all apps one kernel uid). Not adoptable as is here: the broker must be the ancestor of every
  Android process (apklayer starts processes in their own systemd scopes since the Lomiri work) and `/proc/<pid>/mem` of a non-ancestor hits
  Yama ptrace_scope=1; needs Linux 5.9+ (ADDFD); its code is AGPL by sargunv, which apklayer's commercial license (Navotpala) cannot relicense
  without sargunv's agreement (ask before reusing driver.rs).
- **Chosen direction: a userspace binder driver behind apklayer's own libc.** One daemon per instance holds the driver model (nodes, refs,
  transactions and replies, oneway queues, death notifications, fd and fd-array objects, the context manager, freeze, the features libbinder
  checks); written from `drivers/android/binder.c` (or innkeeper's driver.rs if sargunv agrees to dual licensing). Every binder user in
  apklayer goes through bionic_translation, so a thin patch there routes `open`/`ioctl`/`mmap`/`poll`/`close` on `/dev/{binder,hwbinder,
  vndbinder}` (and /dev/binderfs/*) to the daemon over a Unix socket: the receive area is a memfd the daemon maps too, fds travel with
  SCM_RIGHTS, a closed socket is the process's death. No seccomp, no /proc/<pid>/mem, no ancestry requirement, works from separate scopes.
  Caller identity: the daemon reads each connection's SO_PEERCRED, so the per-app sandbox keeps kernel-attested uids (innkeeper gives that
  up). Libbinder, servicemanager, Java and native code stay unmodified, and binder objects move freely between processes.
Steps:
1. Design note (docs/BINDER.md): the daemon's protocol, the driver model's scope, what libbinder's `/dev/binderfs/features` and
   BINDER_VERSION must say, threading (looper spawn, BR_SPAWN_LOOPER), oneway ordering, the freezer (ActivityManager), buffer allocation in
   the memfd, fd lifetime on failed transactions.
2. Prototype: the daemon plus the bionic_translation patch; the existing `binder` and `host-binder` test groups and UiBench run on it;
   round-trip and throughput against kernel binder (a microbenchmark like innkeeper's), on the x86 PC and arm64.
3. Then everything: servicemanager, hwservicemanager, SurfaceFlinger, audio, the hub and apps on the daemon; the full suite on it;
   binderfs becomes optional (kept as an option only if it stays clearly faster for graphics/audio), then removed from setup, the deb's
   unit and the manager's first-run check; Flatpak without its host step.
4. Measure the hot paths (SurfaceFlinger transactions per frame, audio) before dropping kernel binder; a second daemon thread or sharded
   locks if one thread saturates.

State (2026-11-08, branch `userspace-binder`): steps 1 and 2 done. Design note `docs/BINDER.md` (protocol, driver-model scope, threading and

## Design notes that still hold
- **Storage volumes** (user's design, 2026-10-28): each instance has its own `/storage` (`$XDG_DATA_HOME/apklayer/<n>/storage`); volumes Internal storage (`<storage>/emulated/0`, `/sdcard`), Home (`linux-home`) and Linux root (`linux-root`); since 2026-11-09 also the desktop's removable drives (public volumes `/storage/<fs uuid>`, HostVolumes.Removable). Apps' getStorageVolumes: the emulated and public volumes only.
- **Window decoration**: the shell draws an Adwaita-style header bar itself (`bridge/shell/decor_draw.c`, cairo): 46 logical px, Back on the left, minimize/maximize/close on the right; light/dark from gsettings when a window opens.
- **Splash**: until an app presents its first frame, `bridge/shell/splash.c` shows its icon on a colour taken from it.

## Mobile window style (2026-11-05; built, verified on UTM with a simulated phone panel)
Done: `window-mode` setting (auto|mobile|desktop, instance-wide or `window-mode.<package>`; CLI, hub, manager Properties page and the app's detail page; live), mobile style (maximized, no title bar, navigation bar with Back over the bottom (Home removed 2026-11-09, owner: the compositor has its own), its height an inset for the app), density from the output's physical size (`bridge/shell/mobile.c`; checked against the Volla X23's real wl_output: 720x1560, 65x140 mm -> 280, docs/HALIUM.md), ro.sf.lcd_density from the display at stack start, immersive mode (an app hiding the navigation bar reaches the shell: robolectric 0019, the inset goes to 0 and returns; tested in `mobile`). (Home, removed 2026-11-09, minimized the window.) Without wl_subcompositor (Lipstick, 2026-11-09) the bar is a layer of the app's virtual display (docs/HALIUM.md, Sailfish OS); open there: the pointer on that strip goes to the app (touch only), and a launch whose window is not a virtual display's (none today) would have no bar.
Decisions: Recents: none. xdg-shell has no request for a compositor's overview; the shell would need a compositor-specific protocol (Lomiri has none we could use), so the bar has Back only (Home removed 2026-11-09) and the compositor's own switcher does the rest. Landscape: the bar stays at the bottom (Android's phone bar moves to the side). Doing it means a vertical bar (drawing, hit test in pointer.c/touch.c), a width in CONFIGURE and a side in `NavigationBarInset`: more than navbar.c/geometry.c; and Lomiri on the X23 runs portrait-only for app windows today. Revisit when a rotating compositor is in use.
Host dialogs (2026-11-08): in the mobile style the hub's questions (HubInstallDialog) are full-screen pages with big buttons, answered by touch; the manager's dialogs are full-screen pages on compact windows (PageDialog). Needs a human check: a finger on the Sailfish page with the phone unlocked (only the shell's wl_touch path was driven; the phone has a security code), and the same on Ubuntu Touch after a deb of this tree (shell + host-classes.jar) is installed; the look of the page and of the manager's pages on the phones.
