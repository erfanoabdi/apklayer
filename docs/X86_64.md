# apklayer on x86_64 (a PC), and what was done to get there

The device-library route (Android's own libraries on bionic_translation, on kernel binderfs) was built and tested on arm64 (UTM VM). This file is the way to the same on an x86_64 PC.
Nothing of it could run on real x86 hardware here; what was verified is listed under "Verified".

## What comes from the OrbStack tree (`~/los24` in the machine `ubuntu22-x86`)

`scripts/stage-x86_64.sh` (run on the Mac; it re-runs itself inside the OrbStack machine) writes `build/x86_64/apklayer-x86_64-stage.tar`:

| In the tar | From |
|---|---|
| `android-x86_64/lib64/` | the closure of `deps/android-libs.list` (the 402 libraries of the arm64 set): `out/target/product/generic_x86_64/system/lib64`, the APEX and module directories, and `vendor/apklayer`'s own modules built for x86_64 (`out/soong/.intermediates/vendor/apklayer/**/android_x86_64_*_shared`) |
| `android-root/` | the files Android reads at fixed paths (`scripts/collect-android-root.sh` with `ANDROID_PRODUCT=generic_x86_64`), apklayer's half of the device configuration, the permission levels |
| `aosp/Robolectric_all.jar` | `out/host/linux-x86/framework/Robolectric_all.jar` (the same file as the arm64 side uses; Java) |
| `javac-shards/` | `out/soong/.intermediates/frameworks/base/framework-minus-apex/android_common/javac/framework.jar*` (`scripts/build-native.sh` lists the `@CriticalNative` methods from them) |
| `bt-libs/` | bionic_translation built for x86_64 (patched), as a convenience; the PC builds its own |
| `libs-missing.txt` | names of the libraries of the arm64 set that the x86_64 build does not have (see "Open") |

apklayer's modules were built with (logged in `CHANGELOG.md`, "Build log"): `cd ~/los24 && source build/envsetup.sh && breakfast gsi_x86_64 userdebug && m libapklayer_allocator libapklayer_attribution libapklayer_audio libapklayer_audioserver libapklayer_codec2 libapklayer_composer libapklayer_egl libapklayer_gltest libapklayer_mediaserver libapklayer_permission libapklayer_servicemanager libapklayer_servicetool libapklayer_sftest libapklayer_surfaceflinger libapklayer_vdisplay mapper.apklayer`.
The tree's own libraries that apklayer patches (libnativehelper, libmedia_jni, libstatspull, libactivitymanager_aidl, libsensorprivacy and a few more, see `deps/android-tree-files.lock`, status `patched`) are the x86_64 GSI's unpatched ones until their patch scripts (`scripts/patch-*.sh`) have been replayed for x86_64 (see "Open").

## On the PC

Ubuntu 24.04 or newer (glibc 2.36+; the tar's libraries are Android's own and do not care), x86_64, a GPU with Mesa GBM/EGL, a Wayland session.

1. Packages: `build-essential meson ninja-build pkg-config openjdk-21-jdk python3 git libwayland-dev wayland-protocols libcairo2-dev libdrm-dev libgbm-dev libegl-dev libgles-dev libunwind-dev libelf-dev libxkbcommon-dev libudev-dev` and GStreamer development packages for the media HAL (`libgstreamer1.0-dev libgstreamer-plugins-base1.0-dev`).
2. Kernel: binderfs (`CONFIG_ANDROID_BINDERFS`, module `binder_linux` or built in); `scripts/vm-binder-setup.sh` mounts it and creates the devices (it was written for the arm64 VM; read it before running it).
3. `git clone` this repository and unpack the tar: `android-x86_64` to `~/android-x86_64`, the rest to `~/x86_64-native` (`android-root`, `aosp`, `javac-shards`).
4. bionic_translation: `git clone https://gitlab.com/android_translation_layer/bionic_translation ~/bt-x86/bionic_translation && git -C ~/bt-x86/bionic_translation checkout 6253dec`, then `scripts/build-bionic-translation.sh ~/bt-x86/bionic_translation` (patches it with `scripts/patch-bionic-translation.sh`, which is idempotent and arch-neutral, and builds; on an old toolchain it adds the shims in `scripts/x86_64/`).
5. `scripts/fetch-deps.sh`, `meson setup b && ninja -C b`, `scripts/build-tree-host.sh ~/x86_64-native`.
6. `APKLAYER_BT=~/bt-x86/bionic_translation/b APKLAYER_ANDROID_LIBS=~/android-x86_64/lib64 scripts/build-native.sh ~/x86_64-native ~/x86_64-native/javac-shards ~/x86_64-native/aosp/host-classes`, then the same two variables for `scripts/install-shim.sh ~/x86_64-native` after any edit of the JNI shim. `bridge/native/android_stubs.c` is generated, not tracked: `scripts/android-stubs.py` (see its header) against the staged libraries.
7. `bin/apklayer install <apk>` and `bin/apklayer run <package>` as on arm64. The CLI finds the staged runtime through `APKLAYER_NATIVE` (default `~/arm64-native` today: set `APKLAYER_NATIVE=~/x86_64-native`, `APKLAYER_ANDROID_LIBS`, `APKLAYER_BT`).

## What is arch-specific in apklayer (checked)

* `bridge/native/bionic_tls.c`: bionic's thread-pointer slots. On aarch64 the preloaded library's TLS block lands at tp+16, where bionic expects slot 2; on x86_64 glibc's static TLS is below the thread pointer, and the words bionic calls slots are fields of glibc's thread control block. The array is aarch64 only now; fs:0x28 (the stack guard) is shared by both worlds. Android code that writes TLS_SLOT_APP/OPENGL/OPENGL_API/SANITIZER/ART_THREAD_SELF would corrupt glibc: the libraries run here do not (EGL and the GLES trampolines are the host's, ART is absent). Go runtimes keep their `g` at TLS_SLOT_APP on arm64 and use their own TLS on x86_64.
* Everything else in `bridge/native` is plain C against glibc; `bridge/ndk/*.c` are generated stubs by `nm`.
* `scripts/*` that name `arm64` take their inputs from environment variables now (`build-native.sh`, `install-shim.sh`, `collect-android-libs.sh`, `collect-android-root.sh`).
* The JNI shim is installed into both architecture folders of the framework jars (`native/linux/x86_64` and `aarch64`), so the same jars serve either machine.

## Verified (on the OrbStack machine, x86_64 Ubuntu 22.04)

* bionic_translation, patched with steps 1-17 of `scripts/patch-bionic-translation.sh`, builds (`scripts/build-bionic-translation.sh`: libc_bio, libdl_bio, libpthread_bio, libstdc++_bio are x86-64 ELF).
* apklayer's native C compiles for x86_64 (preload, aprop; the JNI shim and btload: see `docs/PLAN.md`).
* `scripts/stage-x86_64.sh` ran to the end; every staged ELF is x86-64.

## Open

* Running it: nothing here ran on real x86_64 hardware with a display and a GPU. Expect the first run on the PC to need a few fixes (the arm64 route needed dozens).
* The libraries in `libs-missing.txt` (extractors, codec2 software codecs, vpx, opus, flac: a Mainline or product-specific part of the arm64 set that the GSI x86_64 build does not install in `system/lib64`) and the patched tree libraries above: replay the arm64 recipes (`scripts/patch-*.sh`, `scripts/orb-build-module.py`) for x86_64 when media matters.
* Vulkan (`scripts/patch-vulkan.sh`, `scripts/orb-build-vulkan.py`) was not staged.
