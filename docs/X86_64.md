# apklayer on x86_64 (a PC), and what was done to get there

The device-library route (Android's own libraries on bionic_translation, on kernel binderfs) was built and tested on arm64 (UTM VM). This file is the way to the same on an x86_64 PC.
First run on a real PC: 2026-11-04 (see "Verified on a PC"); what is still missing is under "Open".

## What comes from the OrbStack tree (`~/los24` in the machine `ubuntu22-x86`)

`tools/stage x86_64` (run on the Mac; it re-runs itself inside the OrbStack machine) writes `build/x86_64/apklayer-x86_64-stage.tar`:

| In the tar | From |
|---|---|
| `android-x86_64/lib64/` | the closure of `deps/android-libs.list` (the 402 libraries of the arm64 set): `out/target/product/generic_x86_64/system/lib64`, the APEX and module directories, and `vendor/apklayer`'s own modules built for x86_64 (`out/soong/.intermediates/vendor/apklayer/**/android_x86_64_*_shared`) |
| `android-root/` | the files Android reads at fixed paths (`tools/stage root` with `ANDROID_PRODUCT=generic_x86_64`), apklayer's half of the device configuration, the permission levels |
| `aosp/Robolectric_all.jar` | `out/host/linux-x86/framework/Robolectric_all.jar` (the same file as the arm64 side uses; Java) |
| `javac-shards/` | `out/soong/.intermediates/frameworks/base/framework-minus-apex/android_common/javac/framework.jar*` (`tools/build native` lists the `@CriticalNative` methods from them) |
| `bt-libs/` | bionic_translation built for x86_64 (patched), as a convenience; the PC builds its own |
| `libs-missing.txt` | names of the libraries of the arm64 set that the x86_64 build does not have (empty since 2026-11-04) |

apklayer's modules and the patched tree libraries are built as their 64-bit output files (module names would also build the 32-bit x86 variants), logged in `CHANGELOG.md` "Build log" (2026-11-04): `breakfast gsi_x86_64 userdebug && m out/soong/.intermediates/vendor/apklayer/<dir>/<module>/android_x86_64_shared/<module>.so ...` (vendor modules: `android_vendor_x86_64_shared`) and `out/target/product/generic_x86_64/system/lib64/<lib>.so` for the tree's libraries; `tools/stage x86_64` takes the module outputs of the lock's apklayer/patched libraries first (system/lib64 copies can be older). `deps/android-tree-files-x86_64.lock` lists the result (`APKLAYER_ARCH=x86_64 PREBUILTS=<prebuilts checkout> tools/gen/tree-files-lock.py`). Its `same` means identical to the tree's build output: libbinder and the other patched tree libraries were built from the patched sources, so they read `same` there (on arm64 the staged copies are newer than system/lib64 and read `patched`).

## On the PC

Ubuntu 24.04 or newer (glibc 2.36+; the tar's libraries are Android's own and do not care), x86_64, a GPU with Mesa GBM/EGL, a Wayland session.

1. Packages: `build-essential meson ninja-build pkg-config openjdk-21-jdk python3 git libwayland-dev wayland-protocols libcairo2-dev libdrm-dev libgbm-dev libegl-dev libgles-dev libunwind-dev libelf-dev libxkbcommon-dev libudev-dev libbsd-dev libpipewire-0.3-dev` and GStreamer development packages for the media HAL (`libgstreamer1.0-dev libgstreamer-plugins-base1.0-dev`).
2. Kernel: binderfs (`CONFIG_ANDROID_BINDERFS`, module `binder_linux` or built in); `tools/host-setup/binder.sh` mounts it and creates the devices (it was written for the arm64 VM; read it before running it).
3. `git clone` this repository and unpack the tar: `android-x86_64` to `~/android-x86_64`, the rest to `~/x86_64-native` (`android-root`, `aosp`, `javac-shards`).
4. bionic_translation: `git clone https://gitlab.com/android_translation_layer/bionic_translation ~/bt-x86/bionic_translation && git -C ~/bt-x86/bionic_translation checkout 6253dec`, then `tools/build bt ~/bt-x86/bionic_translation` (applies `patches/bionic_translation/*.patch` with `patches/apply bionic_translation <tree>`, which is idempotent and arch-neutral, and builds; on an old toolchain it adds `patches/bionic_translation/compat/`).
5. `tools/fetch-deps.sh`, `meson setup b -Dbionic_translation=$HOME/bt-x86/bionic_translation/b -Dandroid_libs=$HOME/android-x86_64/lib64 && ninja -C b` (also builds the native runtime: JNI shim, btload, preload, NDK stubs), `tools/build host ~/x86_64-native`.
6. `APKLAYER_BT=~/bt-x86/bionic_translation/b APKLAYER_ANDROID_LIBS=~/android-x86_64/lib64 tools/build native ~/x86_64-native ~/x86_64-native/javac-shards`; after an edit of the JNI shim the same without the shards (the list in `native-runtime.jar` is kept). `bridge/native/android_stubs.c` (checked in, generated against the arm64 set; both architectures' stubs) can be regenerated with `tools/gen/android-stubs.py` (see its header) against the staged libraries.
7. `bin/apklayer install <apk>` and `bin/apklayer run <package>` as on arm64. The CLI finds the staged runtime through `APKLAYER_NATIVE` (default `~/arm64-native` today: set `APKLAYER_NATIVE=~/x86_64-native`, `APKLAYER_ANDROID_LIBS`, `APKLAYER_BT`).

## What is arch-specific in apklayer (checked)

* `bridge/native/bionic_tls.c`: bionic's thread-pointer slots. On aarch64 the preloaded library's TLS block lands at tp+16, where bionic expects slot 2; on x86_64 glibc's static TLS is below the thread pointer, and the words bionic calls slots are fields of glibc's thread control block. The array is aarch64 only now; fs:0x28 (the stack guard) is shared by both worlds. Android code that writes TLS_SLOT_APP/OPENGL/SANITIZER/ART_THREAD_SELF would corrupt glibc: the libraries run here do not (ART is absent). TLS_SLOT_OPENGL_API (fs:0x20) is glibc's `sysinfo`, which only i386 reads: our libEGL keeps the GLES hook table there for Android's libGLESv1_CM, as on aarch64 (aosp/hals/graphics/egl/Gles1.cpp). Go runtimes keep their `g` at TLS_SLOT_APP on arm64 and use their own TLS on x86_64.
* Everything else in `bridge/native` is plain C against glibc; `bridge/ndk/*.c` get weak stubs generated from the real library by `nm` (`tools/gen/ndk-stubs.sh`).
* `tools/build` and `tools/stage` take the arm64 defaults from environment variables (`APKLAYER_BT`, `APKLAYER_ANDROID_LIBS`, `ANDROID_LIBS_SRC`, `ANDROID_PRODUCT`); meson from its options `bionic_translation` and `android_libs` (default: the same variables).
* The JNI shim is installed into both architecture folders of the framework jars (`native/linux/x86_64` and `aarch64`), so the same jars serve either machine.

## Verified (on the OrbStack machine, x86_64 Ubuntu 22.04)

* bionic_translation, patched with what are now patches 0001-0022 of `patches/bionic_translation/` (steps 1-17 of the former script), builds (`tools/build bt`: libc_bio, libdl_bio, libpthread_bio, libstdc++_bio are x86-64 ELF).

## Verified on a PC (2026-11-04)

Intel Alder Lake-N UHD (Mesa ANV, GLES 3.2, Vulkan 1.4), Ubuntu 24.04, GNOME Wayland, 4 CPUs, 11 GB; prebuilts branch `x86_64/` of 2026-10-29 and `common/`, steps of `docs/INSTALL.md` with the x86_64 paths.
* bionic_translation (`tools/build bt`), `meson setup b && ninja -C b`, `tools/build host`, `tools/build native` (shards from `common/javac-shards`): all build; `meson test --suite bionic` passes.
* `apklayer install` of UiBench (framework natives registered) and `apklayer run`: the stack comes up on binderfs (instance devices from `binder.sh <id>`), the app draws with GLES 3.2 on ANV, its buffers reach SurfaceFlinger and the shell as dma-bufs (18 frames in 10 s), the app ends cleanly.
* With the refreshed prebuilts (2026-11-04, the x86-build branch): `tests/run` with `tests/vm/x86pc.conf` (APKLY_VM, APKLY_VM_ROOT=~/apklayer-x86/repo, APKLY_VM_ENV as in `~/apklayer-x86/env`, APKLY_SLOTS=x1 x2): gpu, gpu-window, texture-view, vulkan, vulkan-present (600 frames of an Android swapchain on screen), native, activities, webview (the x86_64 WebView provider) pass; per-instance screenshots show UiBench, the TextureView and the swapchain frames.
* Corpus apps with x86_64 libraries draw (`CORPUS_INSTANCE=x2 APKLY_VM_CONF=x86pc tests/corpus/run.py`): Organic Maps, VLC 3.7.2 (x86_64 build), mpv, FluffyChat (Flutter), NewPipe, OpenTTD (GLES 1 through Android's libGLESv1_CM on gfxstream's translator: Ubuntu's Mesa has no ES 1, so `tools/build gles1 <native>` is part of the PC's setup).

## arm64-only apps (native bridge, Digitalis)

An app with no `lib/x86_64/` but `lib/arm64-v8a/` runs its libraries translated, as an x86_64 Android device with a native bridge does
(`docs/PLAN.md` "Plan: apps built for another CPU", part 1).
* Translator: Digitalis (an arm64 guest for AOSP's Berberis, Apache-2.0), its fork of `frameworks/libs/binary_translation` checked out in
  `~/los24` (android17 abefbe2b, a fast-forward of the tree's commit) plus `patches/aosp/frameworks/libs/binary_translation`. Built in
  gsi_x86_64 with `APKLAYER_NATIVE_BRIDGE=arm64` in the build's environment (`aosp/nativebridge/*.mk`, included through the tree's
  `vendor/extra/{product,BoardConfigExtra}.mk` hooks; without the variable nothing changes): `TARGET_NATIVE_BRIDGE_ARCH := arm64` makes
  Soong build the guest (native_bridge) variants. Build log in `CHANGELOG.md`.
* Staged: the host side (`libberberis_arm64.so`, `libberberis_exec_region.so`, the `libberberis_proxy_*.so`) beside the Android libraries;
  the guest world (`system/lib64/arm64/`, `system/bin/arm64/{linker64,app_process64}`, `system/etc/ld.config.arm64.txt`) in the Android
  root, where the path layer serves `/system/...` from.
* Install (`cli/apps.cpp`): no library of the CPU's ABI, the bridge staged and arm64 libraries present -> those are extracted and
  `nativeRoute=bridge-arm64` is recorded in info.properties (else `native`); `apklayer run` passes `-Dapklayer.nativebridge=arm64`.
* Load (`NativeLoader`, `bridge/native/native_bridge.c`): libnativeloader's steps through `NativeBridgeCallbacks`: `initialize`, the app's
  isolated namespace linked to the guest `system` namespace for the public libraries, `loadLibraryExt`, `getTrampolineWithJNICallType` for
  JNI_OnLoad and every `Java_*` function (shorty from the Java method); `getMethodShorty` answers through JVMTI `GetMethodName`.
  `BERBERIS_FLAGS=glibc-host-thread-id-handoff`: guest threads get bionic thread records of their own (the host's TLS slots are glibc's).
