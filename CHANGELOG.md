## 2026-11-09: `apklayer stop` leaves nothing of the instance running; an app ends with its hub
- Cause (the two follow-ups of "the always-on unit's hub no longer loses to a stray `apklayer hub`"): stop ended the run.* records before the hub, so
  the still-running hub restarted a component host stop had just ended; that launch took the spare (a JVM the holder started, no child of the hub)
  and started a new holder (`app-spare --after N`, detached), which the hub's own shutdown cleanup does not reach and no record listed any more.
  Reproduced on Parallels with the old CLI by the new test: after stop the holders, the hubserver JVM, its component-host launcher and its helpers
  (ip monitor, udevadm monitor) were left.
- Fix (cli/stop.cpp, stopStack moved out of stack.cpp): the hub first (no restarts), then the records, the stack and binderd as before, then, holding
  start.lock (no launch starts a stack meanwhile), every process of the instance until none is left: those whose environment has the instance's
  APKLAYER_INSTANCE and APKLAYER_LOGS (what nativeEnv gives everything apklayer starts; a shell that only exports APKLAYER_INSTANCE is not one), and
  under the sandbox those in the stack's user namespace; never stop itself and its callers, nor the session's shared window shell. Then the
  leftover run.* records go.
- HubClient: a hub that dies takes what the process registered with it (activities, bindings, receivers, alarms, notifications, pending intents), so
  rejoining the next hub would mean replaying all of it. As an Android app process dies with system_server, the app now ends (`the instance hub
  ended: this app process ends with it`, exit 0) instead of running hubless; component hosts already ended from their loop, the hub's own package is
  not affected. Parallels: uibench ended 0.7 s after its hub's SIGTERM.
- Test: tests/vm/stop-race.sh (group hub-services): hello.hubclient bound to its service in a hub-started host, a `component-host` launch started
  right before `apklayer stop`; afterwards no process carries the instance and no run.* record is left (fails with the old CLI, listing the above).
  Parallels (own tree): hub-services, startup, providers, services, activities, broadcasts pass.

## 2026-11-09: Bluetooth channel sockets, server sockets, pairing requests (docs/PLAN.md "Bluetooth and USB")
- `BluetoothDevice.createRfcommSocket(int)`/`createInsecureRfcommSocket(int)` (the hidden calls serial apps reach by reflection): `bluez.py rfcomm
  <address> <channel>` connects an AF_BLUETOOTH RFCOMM socket itself and relays it as the service sockets do (the hub accepts a channel 1-30 in place of
  the UUID). When the app closes a relayed socket the helper now shuts the connection down (before, it lasted until the device closed it).
- Server sockets: `listenUsing[Insecure]RfcommWithServiceRecord` (ShadowHostBluetoothServerSocket, new): the hub starts `bluez.py listen <uuid> <name>`,
  which registers the service with BlueZ's Profile API in the server role, prints `LISTEN`, takes one NewConnection, unregisters and relays it;
  accept() hands it over as a connected socket and starts the next listener at once, accept(timeout) throws "Try again", close() ends the waiting
  listener and wakes a blocked accept. One helper per connection because the app's pipes cannot carry a new descriptor. BluetoothSocket.getRemoteDevice
  is the shadow's (Android 16 keeps it in an Optional the constructor fills: it threw for our sockets). Robolectric's newInstance names a server socket
  constructor this android-all lacks: plain newInstanceOf.
- Pairing: ACTION_PAIRING_REQUEST goes to the app first as an ordered broadcast (variant, key); an app that calls setPin (and aborts) answers BlueZ
  itself, else the receiver after the app's (the system's dialog on Android) asks the hub. The agent registers as DisplayYesNo (Android's capability,
  was NoInputNoOutput): RequestConfirmation asks the person to compare the passkey (HubInstallDialog.ask), DisplayPasskey/DisplayPinCode show the key
  to type on the device. BLUETOOTH_PIN carries the pairing variant and key.
- Tests: the bluetooth group's mock bridges ConnectProfile to an app's server profile (the app's server socket talks to its own client socket), and two
  more devices pair with setPin 0000 (no dialog) and by passkey comparison (answered yes); the channel socket must fail with the kernel's reason
  (Parallels: No route to host; the x86 PC's real adapter: Host is down after paging). Parallels and the x86 PC: bluetooth passes. On the x86 PC's
  real BlueZ `bluez.py listen` registered the server profile (LISTEN), nothing paired.

## 2026-11-09: the always-on unit's hub no longer loses to a stray `apklayer hub` (the restart that left instance ut dead)
- Cause: `apklayer hub` that finds hub.lock held waits for that hub and returns 0 (cli/run.cpp runHub). In apklayer-instance@<id>.service that return ends the unit's main process with success, and its ExecStopPost `apklayer stop` then ends the instance, the other hub included. The other launcher comes from the old stack: processes started while the stop runs survive it (on Parallels the hub restarted a component host `stop` had just killed; the host and its spare holder outlived the sweep, the host's HubStartup ran `setsid apklayer hub`, a `wait hub` started a stack). Over a restart that launcher takes the free lock before the unit's new hub.
- Fix: in its own always-on unit the hub takes over. It ends the launcher that holds the lock (the pids in hub.pid), then starts its own hub. A launcher now writes its pid to hub.pid as soon as it holds the lock, so a launcher still starting its stack can be ended too; a launcher outside the unit keeps the old behaviour (it waits, then returns). ExecStopPost and the lock are unchanged.
- Test: tests/vm/hub-unit.sh (group hub-services) writes a unit for the test instance with the test's environment. It starts a stray hub, then the unit: the unit must stay active, its MainPID must be hub.pid's launcher, with one hub JVM; then the same checks after `systemctl --user restart`. Before the fix it fails with "the unit is deactivating once the stray hub ended". Parallels (own tree): hub-services, startup, push pass.
- Volla X23 (instance ut): with deb lazy4 the same stray sequence left the unit inactive with no hub (reproduced). With deb 0.4.7~git20261109.hubunit (this commit, built on Parallels with tools/release/build-deb.sh, ~/speed78/apklayer-hubunit.deb) the unit's hub ended the stray hub (exit 143) and stayed the only one; restart, and dpkg -i followed by restart, gave one hub owned by the unit. The phone is back on lazy4 (runtime 0.3.4), active with one hub.
